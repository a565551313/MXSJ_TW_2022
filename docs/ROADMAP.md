# 项目路线图：以可验收闭环推进

更新：2026-10-18。本文是**建议路线**，不是已实现功能、完成率、工期承诺或自动开发授权。
原路线图建立轮仅更新文档；后续用户已授权本地 SQLite 实现，第一阶段见 [local_server](../local_server/README.md)。阶段 C 的账号／会话／角色元数据已开工，TCP／进图与 PostgreSQL 仍未完成，不将部分基础当作整阶段通过。当前事实与检查结果以 [STATUS](STATUS.md) 为准，长期规则见 [AGENTS](../AGENTS.md)。
后续每阶段须明确授权范围、负责人、固定输入和退出条件；不因列入路线图就自动改代码、发布或合并。

## 文档和证据的分工

- README：定位、能力、入口，不重复维护测试数字。
- STATUS §1–§2：唯一当前版本、分支、实测、风险和下一步。
- 子项目 README：使用方式、能力边界；DESIGN：决策及尚未实现的设计。
- evidence：绑定代码基线／输入摘要的实际检查记录；旧报告保留原日期，不覆写成新验收。
- archive：被取代的快照；仍被引用的 STATUS 编号历史章节先原位保留。

## 阶段 A：基线治理

**前置条件**：原始包摘要匹配、工作区归属明确；不要删除客户端文件来缩小仓库。

产物：
- 当前事实一致的文档与可复现命令（本轮范围）。
- 后续建立 Linux 核心／前端 CI 与 Windows 交付检查，分开报告 GUI 和外部材料跳过。
- Python 依赖锁定方案、前端开发依赖安全升级评估。
- Mock 启动与客户端写入分离的设计和回归；默认网络暴露的治理方案。

验收：
- 版本与源码元数据一致；当前状态没有重复冲突；相对链接可解析。
- 架构、Catalog/API、共享核心、手册来源校验、前端检查可重复运行。
- GUI／原生验收缺失时明确显示未执行，不能以通过数量抵消。
- 依赖审计非零有逐项处置或有范围的风险接受，不能直接 `audit fix --force`。

**本轮没有建立 CI、升级依赖或改变 Mock 行为。**

## 阶段 B：原生交付验证

**前置条件**：完整、已备份的 Windows 客户端测试副本；合法获得的目标资源及固定版本。

产物：真实资源最小回归集、源码与工具摘要、生成包差异清单、Windows 操作回执、回退步骤。

验收：
1. 资源/UI：打开→导入／修改→保存新包→重开→再次编辑；未改条目逐字节不变。
2. 脚本：候选人工核验→对应标准 VM 编译→原生转换→独立读回→真实客户端加载／交互。
3. 校验使用独立原生依据，不只使用同源编码器／解码器；未知 opcode 和固定容量限制不放宽。
4. 保存失败、取消、错误来源或输出别名不得损坏原包及用户草稿。
5. 每份验收注明版本、输入 SHA、场景、实际结果；用户确认原位包不等于完整重编译新包通过。

停止条件：加载崩溃、身份无法绑定、参数歧义、独立校验不一致。先恢复已知状态，不继续盲发补丁。

## 阶段 C：正式服务端最小链路

**前置条件**：冻结最小协议样例与字段依据、明确认证方案和存储约束。Mock 只贡献经核验的报文知识，不直接继承其认证／存储实现。

范围：

```text
TCP 帧处理 → 握手 → 账号认证 → 创建／选择角色
          → PostgreSQL 持久化 → 单一地图 → 断线重连 → 重启恢复
```

产物：可运行的模块化单体、迁移脚本、会话状态机、固定报文测试和故障测试。
第一版不先引入微服务，不同时展开 21 个业务责任区。

验收：
- 错密码不能登录，角色必须属于已认证账号；快速重登验证票据、用途和有效期。
- 接管后旧连接／旧队列消息不能继续越权修改状态。
- 重试创角不重复；数据库提交失败不能回复成功；提交结果未知时按幂等键查证。
- 角色在服务重启后可恢复；JSON Mock 不作为正式数据库。
- 帧长度、握手阶段、队列与连接资源有界；畸形包／慢连接测试可复现。
- 使用一个明确的测试地图；没有可信碰撞的区域不能默认为可通行。

设计依据：[INTERFACES](../server/docs/INTERFACES.md)、[GATEWAY](../server/docs/GATEWAY.md)、[安全与 GM](../server/docs/GATEWAY_SECURITY_GM.md)。这些仍是设计约束，不是运行实现。

## 阶段 D：最小玩法闭环

**前置条件**：阶段 C 的权限、持久化和幂等基础通过。

范围：NPC 对话 → 接任务 → 完成一个简单目标 → 领取一次奖励。

验收：
- NPC 选项绑定角色、NPC、距离／状态及有效期；不能信任客户端自报奖励。
- 任务条件在服务端检查；领取标记、背包／货币、账本与幂等记录在同一事务提交。
- 重复提交、断线重试、提交中断不重复发奖；背包满或条件不符不会部分成功。
- 客户端得到一致反馈，服务重启后仍可验证领取结果。

不在此阶段同时扩展所有任务、交易、公会或商业化系统。

## 阶段 E：地图与战斗扩展

**前置条件**：数据经复核准入，不将 batch_001 直接复制进 game_data；未知数据保持隔离。

产物：可信碰撞／区域策略、移动与交互权限、战斗规则核心、表现协议适配和结算事务。

验收：
- GIRB 使用固定真实样本及原生独立对照；「1034/1035 的统计」是 0.1.0 时代的历史缺口，
  已由 map_editor v1.0.0 在 101 张客户端地图语料上以 **11,763/11,763 零失败**取代。
  但该语料不随仓库分发，「全量」只指该次语料，**仍不能推广为任意地图的普遍覆盖**；
  服务端侧若要依赖碰撞数据，仍需按自身样本重跑并做原生独立对照。
- 规则执行与客户端表现队列分离；显示结束不等于服务端结算提交。
- 固定随机种子可复盘，非法指令、超时行动、掉线恢复有确定结果。
- 战斗奖励结算幂等、可恢复；客户端技能显示数据不被当作完整伤害公式。

## 并行与交付约束

可以并行做独立工具回归与资料复核；跨模块事务、认证和会话权威不能各自猜接口。
每次交付分列：**实现内容／本轮已验证／仍待验证**。不使用笼统的“全部可用”或总体百分比。
许可证、外部语料、客户端二进制和恢复引擎的分发条件须单独确认；不提交大生成包。
