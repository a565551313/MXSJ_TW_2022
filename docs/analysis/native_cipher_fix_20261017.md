# 脚本编辑器 0.6.0.dev7：native XOR 分段修复

## 结论与范围

用户确认原位包“你的可以，有列表了，加载成功”后，授权修复脚本编辑器。
问题不是用户贴错文件：旧研究catalog存在分段错位，甚至重复/缺失键。
旧解码器和写回器共用这些参数，能同源往返不代表客户端能解密新布局。
本次修正读取、路径索引、语料参数校核及完整重编译写回的共同参数入口。
原始包、原catalog及其SHA不改。输出覆盖、固定扩展长度、未知opcode等护栏保留。

**编辑器核心已修复并回归；修正后完整重编译包尚未在Windows/游戏内验收。**
用户先前验收仅属于SHA `4bf116d0...`的原位包，不能外推为本轮新输出包已验收。
本轮不分发新的游戏FLS，现有可用包不要求更换。

## 客户端依据

只读 `mxmain.dll`，SHA256
`637331b54f7fa9fa6c236fa7f9ac8a8b27f228bd46d05046fdccddf52fbe424d`。

- `0x45D403..485`：以import basename生成seed。`0x45D477`回跳
  `0x45D415`而非`0x45D413`，EBX只清零一次，再XOR累积所有字符贡献。
- 第i个字节，n=i+2：i<5时迭代`(n+5)*(n-1)*n`次，否则`(n+5)*(n+1)`次。
  每轮`v ^= (v*0x7e79+0x029a139f) % 0x7879`。
- `0x45D48B..529`：每段长度`size//5 + seed//256`，key为seed低8位；
  段后`seed ^= (seed*0x788b+0x024543df) % 0x7f63`，到实际负载末端截停。
- 初始/后继seed均在0..32767；有完整、唯一五键序列时，仅128候选即可反推精确seed。
  穷举32768状态发现32766个不同序列，即存在两对碰撞，不能任取第一个结果。
- 原catalog有539行不能唯一按完整五键直接反推，包含小模块重复键等情况。
  额外以候选内嵌文件名的原生name-seed和`mx_hash(basename+b'.s') == entry_id`
  双校核，然后重新解密核名。原表只提供线索，不作为最终cipher回退。
  无提示时搜索有界128候选、最大1MiB；无唯一匹配仍拒绝。

实现：`core/vm/py25/cipher.py`和`keys.py`。`module_paths.py`和
`corpus_recovery.py`的直接profile构造同步校准，inspection/native、workflow和
native_build经统一入口使用新参数。mxhash从共享真源vendor，不另造哈希算法。

## entry918 的直接证据

size22441，basename `dgtuieditor`，seed6141，keys253/168/139/169/142。

| | 边界1 | 边界2 | 边界3 | 边界4 |
|---|---:|---:|---:|---:|
| 旧catalog | 4508 | 9012 | 13542 | 18067 |
| 客户端算法 | 4511 | 9012 | 13542 | 18070 |

第一处把嵌入filename的`script`前三字节异或了85（253^168），得到`&6'ipt`。
第四处把`m_dOrgWidgetInfo`前三字节异或39（169^142），得到`JxCOrgWidgetInfo`。
后者被旧恢复源码通过intern引用带入3个函数、5处源码引用；仅修写回cipher不会自动
修复用户已保存的旧稿。旧v1/v2继续暂停，不能照抄旧源码。

验证用v3完整源码另存`tools/client_patches/native_uieditor_open_list_v3/`，保留628行，
将上述5处还原为native真名，未覆盖旧v2文件。附完整文件和相对暂停v2的diff。
与正确解密原模块比较，60个code object中只有GetFileInfo的语义签名不同；其他59个
指令、头、解析后的常量/名字/局部/闭包及filename相同，忽略源码行表和intern编号。
不执行恢复模块，不据此保证游戏业务语义或启动成功。
