# 内置 UI 编辑器打开列表为空：代码追查

日期：2026-10-17。依据：用户截图显示本地 `interface/dialog4` 中有三个由内置编辑器创建的数字命名 `.dlg`，打开和回车搜索均为空，无可用报错日志。本次不要求用户重复测试，不修改客户端。

## 查到的确定问题

原生“打开”把开发用目录表当作强制前置依赖，而且是在弹出窗口以后才取目录数据。目录表导入/取值失败时，本地目录扫描根本不会执行。代码没有在这条链路中提供本地扫描回退或用户可见的失败提示。

这是确定的代码脆弱点。它与截图中的表现吻合，但静态检查不能证明用户正在运行的客户端当时一定抛出了 ImportError。

## 调用顺序证据

偏移均为转译后的函数内部字节码偏移，不是 FLS 偏移。只解码和解析字节码，没有执行恢复代码。

### entry 918：dgtuieditor.CUIEditorDgt.OpenExplorer

- 0—6：`explorer.ShowExplorer()`；窗口先构造出来。
- 12—24：求值 `oExplorer.Create(self.GetFileInfo(), ...)` 的第一个参数。
- 69：才调用 `Create`。如果前面的参数求值失败，这一步不会到达。

### entry 918：CUIEditorDgt.GetFileInfo

顺序等价于以下说明性伪代码（不是恢复源码，也未执行）：

```python
import file_interface
base = file_interface.FILE_INFO
local = self.GetTmpFileInfo()
return self.CombineFileInfo(base, local)
```

对应偏移：6 导入目录模块，15 读取 FILE_INFO，27 才调用本地扫描，45 合并。
整个函数没有异常处理，也没有“目录表不存在就只显示本地文件”的分支。

### entry 993：explorer.CExplorer

- `__init__` 加载 `dialog4/explorer.dlg`，把 `m_dFileInfo` 初始化为 `{}`。
- `Create` 在偏移 94—97 才将目录表赋给 `m_dFileInfo`；偏移 103—109 调用 `RefreshExplorer`。
- `RefreshExplorer` 在偏移 6—15 直接访问 `m_dFileInfo['.']`，没有缺省根目录保护。
- 搜索也依赖同一份目录表；搜索不是一次重新调用磁盘扫描的操作。

因此，搜索无结果并不能排除目录初始化失败。上一轮让用户改搜文件名没有解决前置数据依赖，应停止重复这类操作。

## 目录表究竟来自哪里

entry 3931：`script/uieditor/getinterfacefilelist.py`。

- 主程序使用开发机路径 `E:/MX/client/trunk`。
- 遍历 interface/misc/item/config/script，输出文件名模式 `file_%s.py`。
- `RecordToFile` 写入 `#coding:gbk` 和 `FILE_INFO = <pprint 格式化字典>`。

所以 `file_interface` 是预生成的开发资源清单模块，不是 `interface.fls`，也不是用户保存的 `.dlg`。这个生成器不是正常“打开”流程中的自动步骤；不能建议用户直接运行带硬编码开发路径的脚本。

## 本地文件为什么应该能被看见

- 保存：3495 `SaveCurFile` 写 `os.getcwd()/interface/<相对布局路径>`。
- 扫描：918 `GetTmpFileInfo` 遍历 `'.\\interface'`，构造 `'.'` 根和 `'.\\dialog4'` 子目录，保存 `sFileList/sDirList`。
- 普通列表按 `.dlg` 后缀过滤。截图中的扩展名与此一致。
- 在工作目录未改变、且前置目录表加载成功的条件下，这两个路径指向同一个本地目录。不应要求用户为了绕过目录初始化依赖反复移动文件。
- 原生 os.walk 默认还会吞掉 listdir 的 OSError；这是另一项诊断薄弱点，不是本轮已确认的实际磁盘错误。

## 修复应落在哪儿（尚未实施）

1. `GetFileInfo`：开发清单作为可选输入，ImportError 或目录表不合式时仍走本地扫描；区分并报告故障，不使用空泛的 catch-all 掩盖问题。
2. 保证根记录 `'.': {'sFileList': [], 'sDirList': []}`，再合并本地扫描结果；校验目录节点结构。
3. `OpenExplorer`：先取完整目录数据再调用窗口显示/初始化；失败给出具体原因，避免一个空窗口假装打开成功。
4. 目录扫描使用明确的绝对根目录，并提供扫描失败的提示，不靠没有回调的 os.walk 静默吞错。
5. 这不是换目录或换字体能解决的修复。实施需要独立、可回滚的客户端脚本补丁，不能直接修改锁定原包；还需按原生字节码工具链验证。

## 追加：已定位原生模块加载入口

`mxmain.dll` 的方法表给出 `C_sys.PkgImport` → VA `0x45D1D0`。
其流程：查 sys.modules 缓存；尝试读取 script 资源组中的 `<模块名>.s`；
资源读取失败时调用普通 Python 导入入口 `0x4EE470`（与内建 __import__ 同入口）。

因此：

- **不是只能修改 script.fls。** 缺少 `.s` 资源时，原代码存在普通 `.py` 导入回退。
- 已按正确键 `file_interface.s` 检查原包全部5,002条目录，确实没有 ID `0x3caabef5`。
  这比之前仅在成功解析模块中未找到定义更强，但仍只针对仓库这份原包。
- 正确键已交叉验证：4,951个已取出路径候选的 basename + `.s` 与目录 ID 一致。
  不再沿用“script.fls不走资源哈希”的旧判断。
- `.py` 必须位于普通导入的实际 sys.path，而不是随意放在 interface 文件夹。
  原生字符串中虽有 CPython 默认搜索路径，启动初始化部分受保护，尚未证明实际
  sys.path 未被改写。本轮不提供未经核实的具体安装目录，不要求用户盲试。
- 把 `.py` 改名 `.s` 不可行：`.s` 资源内容会走定制解码和 marshal 读取，不是纯文本执行。
- 创建 E 盘开发目录不是导入要求，与这条运行时路径无关。

字节码/机器码只读检查，未启动客户端、未执行恢复模块、未修改原包。
