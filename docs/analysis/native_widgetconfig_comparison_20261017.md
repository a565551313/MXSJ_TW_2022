# 原生 UI 配置与外置编辑器对照

日期：2026-10-17。范围：只读调查；**没有改编辑器功能、没有运行恢复出的游戏代码、没有改原包或密钥库**。

## 先说结论

不是“控件字段大量写错”。原生编辑器有 **31 种默认模板、22 种工具栏入口**；外置编辑器有 **38 种模板**。31 种共有模板的**字段集合逐项相同**。

真正要修的是：**文本对齐的解释、空列表的编辑类型、资源框的绘制假设，以及预览能力说明**。此外，当前新建默认值来自布局统计，不是原生编辑器的默认值；这两种来源应该区分，而不是全部替换。

用户此前已经在 Windows 验证过“添加组件后游戏会显示”，这项结论保留。本轮是静态对照和一个纯函数实验，不是新的 EXE/游戏画面验收。

## 证据与方法

- 直接读取 `data/script.fls` 的 entry 3853：`script/uieditor/widgetconfig.py`，沿已有解码/转译管线取得可解析结构。
- 对模块顶层仅解释常量、字典/列表构建和赋值；导入、函数定义只记符号，不执行 import、函数、eval 或模块代码。解释结束检查栈为空。
- 取得完整 `DEFAULT_VALUE`、`DEFAULT_CONFIG`、`COMMON_CONFIG`、类型标签和工具栏列表。顶层赋值偏移分别见证据 JSON；这些是**转译后的字节码偏移**，不是 fls 文件偏移。
- 进一步反汇编 entry 2751（属性面板）、3495（字体初始化）、579（combdialog）、1156（textwidget）、1963（progresswidget）、4055（framewidget）、4537（mxui/ui），交叉核对配置与创建/绘制行为。没有执行这些模块。
- 非 ASCII 字节同时保留 `raw_hex`、Big5 和 GBK 解码。中文标签多为 Big5，资源路径可为 GBK，不能整份用一种编码硬解。默认值比较先规范字符串，避免 Python 2 bytes 与 Python 3 str 造成假差异。

可核查附件：

- [原生表快照](evidence/widgetconfig_20261017/native_tables.json)：原始非 ASCII 字节、函数符号、转译 pyc SHA、赋值位置。
- [逐类型默认差异](evidence/widgetconfig_20261017/default_comparison.json)：31 种共有模板的全部字段和值差异，包括名称、样例文本、路径等；不是“错误计数”。快照会将 tuple/list 都序列化为 JSON 数组，不能据此证明两者原始容器类型相同。
- [空列表编辑实验](evidence/widgetconfig_20261017/sequence_probe.json)：只提取并调用外置编辑器自身的 `_parse_sequence`，不加载 Qt，不执行游戏代码。
- [关键字节码摘录](evidence/widgetconfig_20261017/bytecode_excerpts.md)：文本映射、旧文本排版、资源框调用、进度条运行时比例与字体初始化。

外置代码均在 `ui_editor/src/ui_editor/` 下；以下用相对模块名定位，避免行号随修改失效。

## 一、确定理解不准或有实际缺口

### 1. 新旧文本对齐不是同一套数字【优先修】

原生配置：

| 类型 | 数值含义 |
|---|---|
| `CTextFrame`（旧） | 0=右对齐，1=中对齐，2=左对齐 |
| `CTextFrameEx`、`CRichTextFrame` | 0=左上，1=中上，2=右上；3=左中，4=中中，5=右中；6=左下，7=中下，8=右下 |

依据：3853 的 `GetOldFontAlight` / `GetFontAlight`、各类型 `iAlign` 配置；2751 `CreateListBox` 按属性值加一选中列表项。579 的旧 `CTextFrame.SetText` 进一步确认：1 取居中偏移，2 取零偏移，其余取右侧偏移。

外置 `core/painters.py::_draw_text` 统一用 **0=左、1=中、2=右，其他=左；全部顶对齐**；`_paint_text` 给三个类型传入同一个绘制函数。

后果：旧控件的 0/2 会反；新控件的 3—8 没有正确解释，例如外置默认 `CTextFrameEx.iAlign=4` 本应居中，当前却画到左上。**4 本身不是非法默认值，错误在绘制解释。**

还要注意：旧文本按最长一行的实测宽度对齐、再计算自身尺寸，不完全等同在外置的固定矩形内对齐。修映射与修尺寸应分别验。

### 2. 空的数字列表编辑后会变成字符串列表【优先修】

当前外置 `ui/property_panel.py::_parse_sequence` 用原列表第一个元素判断类型；原列表为空时默认 `str`。

实际纯函数实验：

```text
原值 []，输入 255, 0, 0  → ['255', '0', '0']
原值 []，输入 100, 100 → ['100', '100']
原值 [0, 0, 0]，输入 255, 0, 0 → [255, 0, 0]
```

外置默认的 `lColor`、`lEnterColor`、`lSubWidth` 等多处恰好为空数组。因此这不是只影响罕见输入：新建控件后填颜色/列宽，会得到与原生配置不一致的元素类型。

原生的颜色转换器生成整数数组；列宽是列表；而 `lRelationName` 应是名称字符串列表。不能统一把所有列表强转 int，也不能照搬原生的 eval。

外置 `_color_from_value`、`_paint_table` 过滤整数，所以上述字符串列表还会导致预览回退默认颜色/列宽。对游戏读取的影响仍需按实际加载函数核对，**不把它说成已经证明游戏必崩**。

建议：按“控件类型＋属性名”定义数字/字符串序列语义，严格校验失败并提示，不悄悄留下字符串。保持安全解析。

### 3. 边框资源不总是“一张图拉伸”【确定存在模型缺口】

外置 `_paint_frame` 为 `CFrame/CHFrame/CVFrame/CBorder` 共用整图拉伸；`CPngNineFrame` 的 `_paint_nine` 假设源图固定三等分。

原生 579：

- `CFrame.CreateImages` 根据类型选择原生框创建函数；`CPngNineFrame.GetType` 返回另一类型标记。
- `CreateFrameBase` 可组合 `top/`、`bottom/`、`middle/` 资源。
- `CreateHFrameBase` 可读取 `left`、`right`、`middle` 等分片；`CreateVFrameBase` 可读取 `top`、`bottom`、`middle` 等分片。
- `GetFileExtention` 区分 `.igs` / `.png`，不是所有框都直接加载 `sFileName` 指向的一张整图；还存在原生新框分支。

因此，把这些类型一律当普通图片，确实会漏掉可用的原生资源组合。**这不等于所有 PNG 都应该改成目录分片，也不证明所有九宫格都按同一方式切割**；新框分支、样式选择和真实分片尺寸应分别追踪。现有固定三等分只能称近似，不能当原生规范。

另外，原生属性面板中 `CHFrame` 只给宽度、`CVFrame` 只给高度；原生最终尺寸来自创建后的 `GetSize`。外置 `effective_size` 用图片尺寸或 80×24 等兜底，不等于客户端的测量结果。

### 4. 进度条与滚动条说明超出了实现【确定】

外置 `_paint_progress` 固定画 **65%**，没有读取 `iValue`；填充矩形是固定 1 像素内缩，没有按 `iOffsetX/iOffsetY/iSpace` 计算。滚动条 `_paint_scrollbar` 固定在顶部画约三分之一高度的滑块，也没有读取 `iValue`。

但 `ui/paint_samples.py` 和生成的 `ui_editor/docs/PAINT_CHECKLIST.md` 写成“按 iValue 比例/位置”。这是**能力说明不实**，不应继续据此判断已经支持动态值。

原生的进一步证据：

- 3853 的 `CProgress` 模板没有 `iValue`。
- 579 → `ui.CProgress.Create` → 4537 → `progresswidget.CProgress`。
- 1963 `SetRate` 的注释和计算都明确：**1000=100%**，会夹在 0—1000；填充宽度为 `int((width - 2*space) * rate / 1000)`。
- `CreateBar` 使用偏移与间隙，某些图片分支还会把间隙加入横向偏移；高度从背景/条资源取得。

所以之前“iValue 为 0—100”的说法没有原生依据。正确方向是区分**布局属性**与**运行时预览状态**；以后即便加入进度滑杆，也不应凭空往布局里写 `iValue`。`iType` 的精确用途不能只凭字段名推断成进度方向。

### 5. 富文本、换行与字体效果仍是近似【缺口明确，完整规则未定】

- `_draw_text` 对所有文本固定开自动换行，没有按 `CTextFrameEx.bAutoNextLine` 分别处理。原生 textwidget 还有 `iShowType` 等运行时机制，不能只靠这个布尔值推导所有文本类。
- 富文本目前只去掉若干 `#` 标记再画纯文本，不能等同原生点击区、链接、表情等排版。`bClick/lEnterColor` 不是“已经复刻”。
- 原生 `Code2Color` 可生成 3/6/9 个整数的颜色数组；富文本 `Code2Color4RichText` 只取第一组。外置颜色函数只使用前三个 RGB，其他组没有参与绘制。**多组颜色的精确原生呈现规则仍待继续核对**，不直接宣称已经确定渐变算法。
- 原生字体列表来自 `ui.lst`，含字体、字号、字重、包边、渐变等信息；`iFont=13` 是字体表编号，不是 13 像素。外置按表取字体这一路方向对，但 `FontDef` 只保留名称/字号/字重，字体效果与完整八字段格式没有复刻。

## 二、只是默认值不同，不能直接判错

`core/defaults_data.py` 注明当前数据来源是 **2,706 个布局、47,139 个控件的统计模板**：字段值众数、宽高中位数、字符串置空。`model.LayoutDocument.new_widget` 深拷贝这份模板，再改唯一名称，不会自动换成原生配置。

原生 `DEFAULT_VALUE` 则是**内置编辑器的新建样例**，也不是所有运行时构造函数的缺省值。两者不同是预期现象。

| 示例 | 原生编辑器 → 外置 | 判断 |
|---|---|---|
| `CMainFrame` 尺寸 | 400×500 → 460×390 | 样例/统计尺寸差异，不是格式错误 |
| `CTable` | 行数 5→10；列宽 `[100,100]`→`[]` | 默认策略差异；空数组的编辑另有上述类型问题 |
| `CTextFrameEx` | 字体 13→0；对齐 0→4；宽 100→84 | 值都需按各自语义理解，不能将 4 判非法 |
| 文本颜色 | `[0,0,0]`→`[]` | 不能武断认定空数组与黑色等价；外置当前空色回退为浅色 |
| `CTextButton` | 样式 41→0；宽 60→80 | 样式编号依赖 `ui.lst`，不应机械覆盖 |
| `CButton.iMsgId` | 0→1 | 统计默认不是分配好的新事件 ID |
| `CVPageButton` | `iMsgId` 0→11；`iTeam` 0→1 | 直接复用可能撞现有消息/分组；是否冲突取决于业务脚本，尚未证明实际冲突 |
| `CImagesFrame` | 原生宽 0 且有资源路径，外置宽 205、路径空 | 不能把 0 解释成必不可见，也不能不看资源就还原最终尺寸 |

建议以后把“原生新建模板”与“现有布局统计模板”分清楚；加载旧布局不做批量重置。资源路径、样式、字体索引都受安装资源影响，不直接把样例路径硬灌给用户。

## 三、原生配置自己也有可疑项，不照搬

1. `DEFAULT_VALUE['CVPngScrollBar']['sWidgetType']` 写的是 **`CVScrollBar`**，外置目前写的是 `CVPngScrollBar`。这是原生模板内部不一致；不能为了“完全一致”把外置改错。
2. `CProgress.iType` 的属性显示名竟是 **`sBarFileName`**。这是配置显示名的可疑项，不是其真实含义的可靠说明。
3. 原生转换器使用 eval 等旧做法。只提取语义，**不把不安全实现移植过来**。

## 四、覆盖范围与面板语义

- 外置多出的七种：`CAutoDlgBase`、`CBitmapFrame`、`CBitmapHFrame`、`CBitmapVFrame`、`CDataWidget`、`CEdit`、`CTitleTableView`。它们并非“原生不存在”：579 的创建器映射中可见相应支持。因此**不能按工具栏列表删掉这些类型**；是否完整预览另论。
- 原生只有 22 个工具栏入口，31 种配置不等于 31 个按钮。工具栏没有出现某类型，也不等于游戏不支持它。
- 原生明确标注 `CTextFrame` 为废弃、`CTextFrameEx` 为推荐。外置当前类型列表直接按类名排序，没有传达这层区别。建议保留旧控件兼容，新建入口标“旧版/推荐”。
- 原生 `COMMON_CONFIG` 只显示名称、X、Y，不能据此删除其它公共字段。原生面板能编辑哪些字段，与文件允许哪些字段，不是同一个问题。
- 外置属性面板主要看当前 Python 值的类型，而非控件语义。例如 `CTableView.bShowBg/bShowBgLine` 原生按 int 转换，不应只凭 b 前缀改成 bool；`sStyle` 原生接受数字并转换 int，其它输入转换成字符串 `'None'`，不是普通任意字符串。
- `CSpriteFrame` 原生默认路径是 `.spr`；外置面板 `_IMAGE_EXTS` 没有 `.spr`，资源挑选存在入口缺口。**这不等同于已经确认底层完全不能解码 SPR**，需要与资源解码能力分开查。

## 五、建议怎么改——待决定，不在本轮实施

**先修确定错的：**

1. 分开新旧文本的对齐映射；加入 0/1/2 与 0—8 的明确测试，特别覆盖旧 0/2 与新 4/8。
2. 引入小规模“类型＋字段”元数据，先覆盖颜色、列宽、关联名称、字体和对齐。修空数组输入类型与非法输入提示；未知字段仍保留。不要大改存储格式。
3. 纠正样例说明：进度条固定 65%、滚动条为固定占位；如新增预览状态，独立存放，不写进 `.dlg`。

**随后补资源规则：**

4. 按原生调用链分别补 H/V 框、目录分片与新框分支、资源决定尺寸，再处理九宫格。不能靠“都三等分”一次覆盖所有框。
5. 再补文本换行、字体效果和富文本，分别标注精确支持/近似/占位。

**默认值最后定策略：**

6. 确认希望新建控件采用原生样例还是统计模板；保留已有布局，不批量改字段。消息 ID/分组不直接继承统计众数，也不凭空声称原生 0 就能解决所有事件冲突。

不需要为本轮调查重复之前整套 Windows 添加控件测试。之后若实施修复，应围绕本次改变的对齐、列表类型和资源框做定点验证。
