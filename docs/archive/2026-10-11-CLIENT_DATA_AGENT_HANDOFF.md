## 数据来源与现有工具假设

主要来源：`data/script.fls`。

当前解析链路为：FLS索引 → zlib解压 → 5段XOR → 自定义Python 2.5字节码转译 → marshal解析 → 受限字面量表重建。

现有工具使用的索引计算方式：

```text
index_offset = uint32_le(archive[8:12])
entry = unpack('<IIII', archive[index_offset + 16 * entry_index:...])
entry_id, a, b, c = entry
size = ((a * entry_id + 0xDF25E) & 0xffffffff) ^ b
offset = ((b * entry_index * 0xF718FE + 0xD59D16C) & 0xffffffff) ^ c
```

下面的边界数字均是**zlib解压后载荷中的零基偏移**，不是FLS文件偏移。现有5段边界与密钥来自历史分析，应独立核对。

旧工具注释提及 `PkgImport` 地址 `0x00457C20`、自定义VM及 `mx.exe` / `mxmain.dll`。这些是调查线索，不是本轮重新验证过的原生算法证据；请确认实际二进制、地址映射和代码含义。

## 建议调查顺序

1. **固定基线**：记录仓库状态、原FLS与密钥库的SHA-256；独立复现报告，不覆盖原证据。
2. **验证底层算法**：优先从客户端原生加载器确定XOR密钥、分段长度/边界生成方式及字节码格式；检查现有评分式求解器为什么允许错误结果通过。
3. **逐项验证候选**：给出原字节、偏移、使用密钥、候选与替代解释、独立支持证据。独立验证可以是实际原生算法对相同载荷的结果，或同版本独立读取结果。没有独立证据时保留为候选。
4. **递归验证目标表**：检查所有嵌套字符串、字段类型、重复键、ID、技能引用、图片映射和错误回退规则。不要只检查名称。
5. **检查静态语义与关系**：宠物详细表中的技能目前是名称而非ID；先可靠恢复技能表，再做名称→ID对应。不要擅自把客户端 `shape`、图片ID、服务端模板ID视作同一个概念。
6. **回归与影响评估**：若改工具，至少覆盖上述正例/反例及此前可正常读取的目标表；如改通用算法，扩大条目回归范围并报告失败/变化清单，不用“可解析总数提高”代替正确性。
7. **给出CSV准入结论**：哪些表/字段可进入待审导出，哪些必须隔离，哪些缺少服务端权威规则。未经充分验证不生成或发布正式CSV。

不要把任务变成“把现有乱码改成看起来正常的中文”。重点是解释错误产生原因，并使正确提取过程可复现。
