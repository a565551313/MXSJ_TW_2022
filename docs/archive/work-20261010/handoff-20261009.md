## 本次完成

- 在分析工作区安装 Ghidra 12.1.4，并为 REA 建立单独的 Ghidra 后端；REA 只读就绪检查通过。
- 使用 REA/Ghidra 对 `mx.exe` 与 `IMProtocol.dll` 做离线静态分析，原始证据分别保存在 `evidence/rea-ghidra-mx-exe-20261009-1229.json`、`evidence/rea-ghidra-mx-exe-20261009-1241.json` 和 `evidence/rea-ghidra-improtocol-20261009-1244.json`。证据索引见 `evidence/E-REA-002.md`，接口结论补记于 `notes/ida-protocol-interface.md` 与 `report/analysis.md`。
- 确认 `IMProtocol.dll` 中存在 `IMP_ConnectNsServer` → `FUN_10001660` → `FUN_10005cb0` → `FUN_10004920` 的静态连接路径。数值 IPv4 分支把端口经 `htons` 转换后写入 IPv4 `sockaddr` 并调用 Winsock `connect`；域名分支采用带 `0x502` 消息的异步解析形式，socket 通知使用 `context+0x503`、掩码 `0x3f`。
- 新增 `tools/loopback_capture_server.ps1`，用于 Windows 本机的下一阶段测试。脚本只绑定 `127.0.0.1:3134`，打印客户端发送字节的 HEX/ASCII，不访问外网，也不返回应用层协议数据。
- 新增 `notes/protocol-artifacts/responsive_loopback_harness.py`，仅绑定 `127.0.0.1`；默认只捕获，只有显式传入 `--response-hex` 才发送测试响应。该 harness 已通过分片 TCP 合成测试，但未接收真实客户端请求。
- 新增 `notes/agent-native-script-binding.md`，由 IDA 9.4 与 Ghidra 独立核验 `0x2714 -> OnServerCmd(int)`；该结果没有把 `ProcessServerCmd` 误标为已绑定。

## 目前不能下的结论

`server.ini` 的静态配置包含多个 `:3134` 候选端点，但并未验证这些地址可达或对应哪个服务。`mx.exe` 导入了 `IMProtocol.dll` 的连接/发送接口，但 Ghidra 目前没有在所查 IAT 槽发现可验证的直接代码引用；不能据此认定 `NsServer` 就是游戏登录通道。登录首包、服务端响应、认证成功和进入地图均未确认；单独完成 TCP 握手不等于协议登录成功。

## Windows 本地测试

1. 在 Windows 电脑复制一份游戏目录作为测试副本；保留原始目录和 `server.ini`。仅在副本的选中服务器记录中把 IP 改为 `127.0.0.1`，端口保持 `3134`，并保留原文件编码。
2. 在 PowerShell 中运行：

   ```powershell
   powershell -NoProfile -ExecutionPolicy Bypass -File .\loopback_capture_server.ps1
   ```

3. 保持监听窗口运行，再启动测试副本里的 `mx.exe` 并选择该记录。脚本输出的 HEX/ASCII 是客户端发往本地监听器的数据；它不会模拟响应。若无数据，先确认客户端与脚本在同一台 Windows 电脑、使用的配置副本正确，且 3134 端口没有被其他进程占用。
4. 将捕获内容连同客户端到达的界面/日志状态交回分析；先解析帧长度、命令字段和发送时机，再决定是否实现最小本地响应。
