## 1. [P1] 回溯基址从 0x801 改成 1，新增的 15 个“成功”扇区全部错误

位置：`map_editor/src/map_editor/core/girb.py:238–245`。

PR 用“成功数量从 129 上升到 144”支持基址改成 1。直接反汇编原始 `mx.exe`：

- `0x60eb42`: `movzbl -0x801(%edx), %eax`
- 后两次读取分别是 `-0x800`、`-0x7ff`。

这确实是 0x801 基址的三字节匹配，不是误读。为避免只凭反汇编文本判断，本次用 Unicorn **隔离仿真原文件 0x60ea90 解压子程序**，与 PR 输出逐字节比较。未启动 Windows 游戏或执行客户端脚本。

| 地图 | 原子程序返回 2400 字节的扇区 | PR cells() 接受 | 与原算法逐字节相同 | 错误却被接受 |
|---|---:|---:|---:|---:|
| 1034 | 234 | 90 | 81 | 9 |
| 1035 | 195 | 54 | 48 | 6 |
| 合计 | 429 | 144 | 129 | 15 |

在独立内存副本中只把该处基址改回 `0x801`，被接受的扇区恢复为 129 个，129 个均与原子程序一致。其他 300 个仍未成功，不能把这个诊断实验当作解码器已修完。

具体反例（扇区编号为零基）：`1034.map` 扇区 69，两边都输出 2400 字节，但从字节偏移 1603 起不同。原输出 SHA256：

`2b106d3d3632b71968d46bedf3d2ac11d29169fce6f55be503742947fdc513d0`

PR 输出 SHA256：

`545fe47bd8292dcf138c25b8cd3405dba94def6c854aa3743a955f44fba70305`

影响：错误数据会被计入 decoded、用于图层/查询和统计，不会按未知数据处理。仅验证取值看起来像 `0xAABB`、长度正确或“不抛异常”，不能证明成功。

**修改要求：**取消无原生依据的经验偏移；进一步修正状态机。给复杂真实扇区增加完整预期字节或输出哈希断言，以原子程序结果作为独立参照。在未验证正确前维持失败/未知状态。PR 的 101 张地图总体统计也应重算，本次没有独立复核全部 101 张。

## 2. [P1] JSON 导出可覆盖源地图，违反只读承诺

位置：`map_editor/src/map_editor/ui/viewmodel.py:303–305`；CLI 调用位置 `cli.py:80–89`。

`export_json()` 将用户给出的任意路径直接交给 `Path.write_text()`，没有源文件或客户端资源保护。CLI 也不限制扩展名，因此即使 GUI 文件过滤器能降低误选概率，仍不能保护底层导出接口。

已在临时目录中的 `2101.map` 副本复现：

```python
vm.open_map('2101')
vm.export_json(source_map_path)
```

文件头从 `0.1M` 变成 JSON 的 `{`，原地图被截断覆盖。原仓库地图未被修改。

**修改要求：**写入前识别并拒绝客户端源资源目标，至少保护当前及已发现的地图文件；覆盖判断需考虑路径归一化、符号链接/硬链接及平台大小写规则。补充源文件哈希保持不变的拒绝测试。只用临时输出路径做正常导出测试不能证明“只读”。

## 3. [P2] 2400 字节是截出来的，超长解码被当作成功

位置：`map_editor/src/map_editor/core/girb.py:260,265,275,284,287–292`。

多个返回路径执行 `bytes(out[:limit])`，然后 `cells()` 只检查结果是否短于 2400。真实输出超过 2400 时已经被截掉，调用方无法发现异常。

真实数据反例：`1035.map` 扇区 40，PR 的未裁剪输出为 **2405 字节**；公共接口返回 2400 并成功返回 1200 格。原子程序则正常返回 2400，且内容与 PR 不同。

最小长度反例：

```python
body = bytes.fromhex('02888888888820000000000000000000440000110000')
# 未裁剪解码：2401 字节
len(decompress(body))  # 2400
len(cells(body))       # 1200，没有抛错
```

另一个相关边界问题：原始 22 字节黄金向量
`02888888888820000000000000000000430000110000`
只保留前 20 或 21 字节，也能被接受；`u16()` 使用补零后 buffer 的长度而非实际 payload 长度验证操作数，缺失的结束标记操作数被人为补出。

**修改要求：**严格检查每次操作数/字面量读取的实际输入边界；输出追加时限制长度，完整结束时验证恰好 2400，禁止静默截断冒充成功。补充超长、截断结束标记和真实扇区回归测试。此问题与第 1 项相互掩盖，单修其中一个不足够。

## 4. [P2] 打包 EXE 无参数启动不会打开 GUI

位置：`map_editor/run.py:23–24`、`map_editor/src/map_editor/cli.py:179–189`、`map_editor/map_editor.spec:44`。

打包入口直接调用 `main()`，而 GUI 分支只有显式 `--gui` 才能进入。首次双击 EXE 没有参数和配置，会走“需要 --scan 或已记住的客户端目录”的退出分支；`console=False` 又使用户看不到终端提示。即使已有目录配置，也只进入 CLI，不会出现 GUI。

隔离空配置目录实测 `main([])` 返回 **2**，输出上述错误，未进入 GUI 分支。**这是入口分派复现和打包配置推导，不是已经在 Windows 构建运行 EXE 的结论。**

**修改要求：**将 GUI 打包入口与 CLI 默认行为分开，或让无参数的冻结程序默认启动 GUI；保留显式 CLI 工作方式。补充无参数启动分派测试，以及 Windows 构建后首次双击的冒烟验证。
