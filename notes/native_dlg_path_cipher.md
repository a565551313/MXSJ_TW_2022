# 原生 LoadFile 的真实绑定与注册 .dlg 路径密钥（2026-10-14）

## 结论与证据范围

本轮用户 phase2-diag1 日志：模块导入/输入设置正常，在 `terms layout begin`
后捕获 `Exception` 并恢复首页。用户说不再卡屏，但不跳条款页。这只确认原生
CCombPanel 构造失败，不能单靠异常类型确认其中哪条语句或原包字节。

继续静态追踪**真实 PyMethodDef** 后发现之前的存储策略有确定缺陷：
原生包内 `.dlg` 不是“从已知明文头自解任意密钥”；它从路径计算密钥。
资源编辑器按路径导入是原始存储字节搬运，之前注册说明却让用户导入明文；
UI 编辑器的缺失布局新增也明确写明文/零密钥。这些明文能被编辑器显示，但
不符合已核实的原生 LoadFile 解密。此错误与用户构造失败日志吻合，实际用户
包的两条存储状态仍需本地修复助手报告，不把可能根因说成已完整实机证明。

只读镜像：`mxmain.dll` SHA-256
`637331b54f7fa9fa6c236fa7f9ac8a8b27f228bd46d05046fdccddf52fbe424d`。
没有加载 DLL/运行游戏函数，没有模拟执行原始机器码。全部地址是此 PE 的 VA。
独立 Python 算术复刻、静态字节签名和调用位移由注册回归测试钉住。

## 1. 为什么前面的加载链推断错了

`.rdata` 字符串 `LoadFile\0` 在 **0x6B4038**。
PyMethodDef **0x7DB2F0** 前三个 DWORD 是
`{0x6B4038, 0x45D580, 3}`，所以真实 `C_sys.LoadFile` 绑定 **0x45D580**。

此前笔记称 `0x461340` 为 LoadFile，这不对：本轮反查该函数的 method table
前项字符串，名字其实是 **ReadFls**（flags=1）。`0x48ECF0` 的线性扫描和
`0x48F170` 的解目录因此不能直接当作真实 LoadFile 的缓存寻址/解密链。
此更正不授权凭猜测改变目录 r1/f1；本次助手逐字保持所有目录字节。

## 2. 真正调用链与密钥

```
0x45D580  C_sys.LoadFile
  0x45D5EA CALL 0x609760
    0x609771 CALL 0x6097F0       资源打开
      0x609AA2 CALL 0x60DD00    包内定位；输出长度/偏移/密钥
        0x60DD11 CALL 0x60E080 路径规范化、哈希、选择加密扩展名
          0x60E105 CALL 0x454860 哈希算术核心
        0x60DD35 CALL 0x60E690 **lower_bound（二分）**：16 字节步长比 entry_id
        0x60DD3D cmp 返回位置==end    → 未找到
        0x60DD41 cmp (返回位置)!=entry_id → 未找到
    0x60977C CALL 0x609790       分配并读全部内容
      0x6097B9 CALL 0x609C80    实际读取与 XOR
```

`0x60E080` 把 ASCII 小写转大写、反斜杠转斜杠；传给 0x454860 的哈希结果
在 EDX。对 `.SPR/.TXT/.MGC/.PFM/.INI/.DLG`，0x60E153 起：

```asm
lea eax,[edx+0x9234ab]
xor eax,0x937f4912
mov [edi],eax
```

所以 `.dlg` 的四字节小端密钥是：

```
key_u32 = ((normalized_path_hash + 0x009234AB) & 0xFFFFFFFF) ^ 0x937F4912
stored = plaintext XOR repeated_little_endian(key_u32)
```

0x609C80 从资源对象 `+0x18` 取密钥；非零时在 0x609CE0 循环对每个 DWORD
做 XOR，尾部对各字节 XOR。**不检查明文头、不自动接受明文、不根据目录 f1
当作这把密钥**。包外直接打开文件是另一个分支，不能拿其未加密行为推包内。

0x454860 的 ROL/两轮 MUL+ADC 与既有 `mx_hash` 的折叠实现对这些非空短
ASCII 路径一致。新助手用独立逐指令算术复刻，并对 1..255 字节随机 ASCII
路径与既有实现交叉比对；不扩展宣称所有中文路径/异常路径都已复核。

### 2.1 包内定位是**二分**，不是线性扫描（2026-10-16 补，指令级）

`0x60DD00` 拿到哈希后，把内存中的目录按 **16 字节步长**交给 `0x60E690`，
该函数是标准 `std::lower_bound`：

```asm
60e69a: sub %esi,%ecx        ; end - begin
60e69c: sar $0x4,%ecx        ; ÷16 → 记录条数
60e6b0: mov %ecx,%eax ; cltd ; sub %edx,%eax ; sar %edx   ; step = count/2
60e6bd: cmp %edi,(%esi,%eax,8)    ; 比较 *(begin + step*16) 与 key（entry_id）
60e6c0: jae → count = step        ; key ≤ mid → 取左半
60e6c2: → begin = mid+1; count -= step+1
```

返回后再判「等于 end」与「`*it == entry_id`」，两者都要求命中位置精确。
内存记录与 `0x48F170` 的输出同构：`+0` entry_id、`+4` f1、`+8` len、`+0xc` off
（命中后 `mov 0xc(%eax)`/`mov 0x8(%eax)` 取长度与偏移）。

**推论（写包必须遵守）**：

1. **包内目录必须按 entry_id 升序**，否则 lower_bound 定位不到；
2. 新增/插入条目后，**其后所有记录的下标都变了**，`r3` 必须按新下标重算
   （偏移闭式变换含 `index`），否则会被“找到但读错长度/偏移”——症状是新条目
   不显示、重开条目数变少、进游戏卡屏；
3. `+4` 的 f1 在这条查询路径上**没有被读取**，`r1` 的真实用途仍未确定；
   “保持 r1 非零”属保守防守，不是已被证实的引擎要求。

`0x48ECF0` 那条线性扫描属 `ReadFls`，**不能**用来推断 LoadFile 的寻址方式；
`notes/fls_path_hash_and_dlg.md` §2 已加对应更正横幅。

| 路径 | entry_id / 哈希 | XOR 密钥字节（小端） |
|---|---|---|
| login/regterms.dlg | 0x25EDC010 | a9 bd 00 b5 |
| login/regform.dlg | 0xF2AECE40 | f9 4b 3e 60 |
| login/service.dlg | 0x14595D67 | 00 db 94 87 |

已知明文头反推密钥是**编辑器解码技巧**。只有当反推结果与这个路径密钥
相等时，才与真实包内 LoadFile 兼容。编辑器能解析并非原生验收。

## 3. 当前修复范围

`tools/registration/repair_interface_layouts.py` 是一次性标准库 CLI：
只检查当前用户 `interface.fls` 的 regterms/regform 两条，不改 script，
不改模板/显示文本/GBK 路径/目录字段，不跑布局代码。

- 已按原生密钥存储：不修；两条都正确时无输出，须另查真实失败点。
- 明文或反推密钥能解为安全 UI_INFO 字面量：保留现有明文字节，按路径密钥
  重加密等长负载。不能识别/非字面量/缺地址/重叠/目录无序则拒绝，不补模板。
- 只读源；临时复制、只改两条已批准字节范围、整文件逐字验证、原子独占发布
  新文件，拒绝覆盖任何已存在输出/源及别名，失败删自己的临时文件。
- 输出长度和头/目录/所有其他负载逐字不变；验证用原生路径密钥回读目标字节，
  不是仅用“从输出头反推密钥”的自洽测试。保留用户编辑、无重新序列化。
- NTFS 等支持硬链接的文件系统可以独占原子发布；不支持时失败，不降级覆盖。

此助手不是完整编辑器修复：两编辑器对**新建路径**的自动加密/验证需独立修正，
不能继续宣称“零密钥新增兼容原生”。已由助手修成正确密文的既存路径，UI 当前
沿原密钥保存的逻辑可以保持该存储形式，但仍须实际游戏回读/交互测试。
