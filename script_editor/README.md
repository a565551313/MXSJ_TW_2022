# MXSJ 独立脚本编辑器 0.6.0.dev12（宽松模式：Ctrl+S 直接写回原包）

## 0.6.0.dev12 补：两个高频疑问的答案

### A. `authored marshal exceeds fixed XOR length; no shrink/rescale`

这条不是 bug，是**固定容量**：py25 的每个 script 条目在包里都有一个固定的解压长度
（`expanded_size`），而客户端的五段 XOR 取参是**用这 5 个 key 和这个长度**一起算出 4 个
分段边界的。所以：

- **改小可以**：新负载比原长度短时，补 `\0` 到原长度再加密（客户端只读到 marshal 结束）。
- **改大不行**：长度一变，客户端算出的边界就跟着变，等价于换了一套加密参数。我们没有
  原生证据证明客户端会怎样处理，因此**只拒绝、不缩放**（这是保守选择，不是能力缺失）。

现在的错误信息会给出三个数字：这次编译出的负载多大、这个条目的固定长度多大、超出多少，
还会顺带告诉你原模块本来留了多少余量。默认路线仍然是**把模块改小**（删/缩不用的代码或
docstring；注释和空白不影响 pyc 大小）。

### A2. 扩容：现在有开关，但仍是实验

`expanded_size` 只是工具从目录里读到的固定长度，客户端并不单独保存那 4 个分段边界——
它每次**按 seed 和它拿到的 size 现算**，并且最后一截「到实际负载末端截停」
（`mxmain` 的 `0x45D48B..0x45D529`：每段 `size // 5 + seed // 256`，循环 5 次，
依据见 [`docs/analysis/native_cipher_fix_20261017.md`](../docs/analysis/native_cipher_fix_20261017.md)）。
也就是说，长度一变，边界会跟着重新算出一套自洽的值；`seed` 只由模块名决定，与长度无关。
从算术上看，扩容是**自描述**的，不需要「另存一份参数」。

0.6.0.dev12 起，工具在「保存模式」菜单里加了一个带风险确认的开关——
**扩充定长条目（实验）**，默认关闭：

| | 关闭（默认） | 打开 |
|---|---|---|
| 比原槽位大的模块 | 直接拒绝，报 `no shrink/rescale` | 按新长度重算分段并写入 |
| 分段边界 | 用目录里的原长度 | `bounds_from_keys(keys, 新长度)` |
| 目录条目长度 | 不变 | `write_script()` 重排 span、重算目录 `r2/r3` |
| 写后回读 | `py25.decode(crypt(inflate(...)))` | 同一套校验，用新长度解密 |
| 本机验收 | 通过 | 通过（同样的逐字节相等） |
| 客户端/游戏内验收 | 不涉及 | **没有**，一次都没有 |
| 写回客户端目录内的包 | 宽松模式允许（每次额外确认） | **拒绝**：只要本次有条目要扩长，工具就报错并让你改用 F6 新包，或走游戏目录之外的副本 |

能自证的部分是实打实的：加密/解密往返、整包回读、未改条目逐字节比对、目录偏移全部重算，
任何一步不等都会在写包前中止。**不能自证的部分是客户端行为**：客户端会不会真的按新长度
重算边界、会不会有别的固定长度假设（预分配缓冲区、总量校验、内存里的段表），我们手上没有
反汇编证据。所以要试就试**游戏目录之外的副本**，并留着 `.fls.bak`；换进客户端后如果启动
或进图崩溃，那不是编辑器写坏了包，而是客户端不接受变长条目。

另外两种「彻底解决」的路子，目前都**没做**，别指望菜单里有：

- **搬进别的条目**：`write_script()` 明确不支持新增/插入条目，只能改写已有条目。
- **换一套参数**：`seed` 由模块名决定，改名不在编辑器能力范围内（会破坏脚本引用）。

也就是说：这条限制的完整解法是「改小」或「打开实验开关」；**「打开开关就等于拿到客户端
验收」这句话不成立**。

### B. 为什么 `r"""\xb9C\xc0\xb8…"""` 这种还不翻译

因为它们**不是字节串**。反编译器（uncompyle6）把 py2 `str` 常量按 UTF-8 解码 + 反斜杠
转义渲染：能当 UTF-8 解出来的字节对变成真字符（`Ұʮɽե`），解不出的变成 `\xNN`，再套一个
`r` 前缀。所以这个字面量本身的值是「反斜杠 + x + b + 9…」这些字符，**不是**那些字节；
直接按 Big5 解它就是编故事。

它的原常量字节可以**反推**：`\xNN` 当一个字节，非 ASCII 字符贡献它自己的 UTF-8 字节，
渲染里那个**单个反斜杠**就是负载里的 0x5C（Big5 里 `功` = `A5 5C`，所以 `成功連線` 会渲染成
`\xa5\xb3s…`——那对反斜杠不是转义，`\xb3` 属于下一个字）。

0.6.0.dev12 起这类字面量也会给出读法，并**明确标注「（反推候选）」**：

| 原文 | 读法 |
|---|---|
| `r"""\xb9C\xc0\xb8\xb1Ұʮɽե\xce\n\n\xb3B\xb2z…"""` | cp950：`遊戲啟動時調用 / 處理遊戲開始登錄流程前的必要初始化操作` |
| `r"""\xc0\xf2\xa8\xfa\xa5i\xa5ΪA\xb0Ⱦ…"""` | cp950：`獲取可用服務器列表，格式為[(房號, 業務服地址, udpPort…]` |

悬停和只读对照对话框都会写清楚这是「反编译器渲染 → 反推原常量字节」，因为**这个原始串
本身的值和读法不是一回事**。用「候选」而不是「还原」，是因为渲染有损：原常量如果**真的**
写着反斜杠加 `xNN` 这几个字符，渲染出来跟一个字节 `0xNN` 一模一样，两者不可区分——
所以这是**有依据的候选**，不是逐字节证明。`u'…'` 仍然不给读法（那是码点，不是客户端比较的字节）。

修复记录：这条 0x5C 规则是审查指出后补上的。之前把这对反斜杠当转义，语料里
`script/login/dgw.py:118` 被读成 `成功xb3s…`；现在读成 `成功連上遊戲服務器後，用此接口告知DGW服務器`。
全语料（61 个 `.py`、69 处字面量）对比：**1 处读法改变（就是它），0 处新增噪声，0 处丢失**。

顺带提醒一条硬事实：这些 `r"""…"""` 文档串**重新编译后字节会变**（py2 的 raw 串不解释
`\xNN`）。目前它们都出现在函数/模块 docstring 里，正常玩法不读 `__doc__`；但如果你要改
这个模块的代码并写回原包，请知道这些 docstring 的字节会跟着变。

> **当前事实入口**：版本来自 `src/script_editor/__init__.py`；最近实测范围以 [STATUS](../docs/STATUS.md) 为准。下方 dev6／dev5 等计数和交付状态是对应日期的历史，不能当作当前版本全量验收。
> 恢复候选、标准 VM 编译、包回读、Windows 游戏加载是不同验收层次。固定容量、未知 opcode、来源摘要与原包保护不放宽。
> 严格模式的新包发布采用不覆盖的硬链接操作；宽松模式经「重新核摘要 → 留 .bak → 原子替换」写回原包。两者都不会半途覆盖。Git 克隆不等于含双编译器／恢复引擎的完整交付 ZIP。

## 0.6.0.dev12：宽松模式——Ctrl+S 直接把改动写回原包（覆盖前留 `.fls.bak`）

以前写包要走三步：`F6` → 清单预览 → 输入一个**尚不存在**的新包名，之后还得自己把新包
换进游戏目录。UI 编辑器早有「严格 / 宽松」开关，脚本编辑器现在也有同一套语义：

- **严格模式**（默认，也是以前唯一的行为）：`F6` 生成新包，原包一个字节不动。
- **宽松模式**：`Ctrl+S` 一步到位——先把改过的 `.py` 存盘，再用精确编译器编译、审计、
  编码成原生负载、回读校验，**写回这些源码所属的原包**，不生成新包、不弹文件名框。
  覆盖前把原包复制成 `<包名>.fls.bak`（固定名，只保留最近一份，由下次覆盖替换）。
  `Ctrl+Alt+S`（编译 → 写回原包）可在非宽松模式下单独写一次，仍会确认。

**宽松改的只是「写到哪儿」，不是「少校验」**。写之前照旧：每条替换都过精确标准编译器、
marshal 审计、原生往返逐字节相等；整包重写后独立回读，未改条目逐条与原文比对。新增的
只有最后一步：关掉读句柄 → 重新计算原包摘要（变了就放弃，绝不动手）→ 复制 `.bak` →
`os.replace` 原子替换 → 替换后再核一次摘要。

点几下：切到宽松模式是**一次性**动作（弹一次确认，之后记住）；此后每次就是按一下
`Ctrl+S`。唯一会再弹框的情况是目标包在客户端目录里（每次保存确认一次）。两种「按了没
写回」的情形不会弹错误框，只在状态栏说明：本条源码还没关联到包内条目（只存了 `.py`）、
以及这个包没有内容变动（`.py` 照存，原包不动）。

一次保存写**同一个包里所有已关联且内容有变动**的条目（`built_source_sha256` 对不上就算
变动；从没写回过的也算），上限 64 条，超过就要求分批。目标包按「当前选中的包」判定，
未选中时用当前标签所属的包。包里没有变动条目时**什么都不写**并说明原因。

安全边界：
- 只允许覆盖**本次构建的那个原包**；其它受保护输入（参数表、已关联源码、别的包）依旧
  一律拒绝（`guard_in_place` 只把原包自己从保护表里摘出来）。
- 原包在保存期间被改动（摘要不符）→ 放弃覆盖；写回失败（Windows 下游戏占用文件）→
  明确报错且原包不变；写回后摘要不符 → 报错并指出 `.bak` 位置。
- 目标包**在游戏客户端目录里**（同目录或上两级有 `mx.exe` / `mxmain.dll`）时，每次保存
  额外确认一次并列出要写回的条目；普通工作副本只在「切到宽松模式」时确认一次。
- 写回后不重扫 5,001 条路径（条目身份与内嵌文件名不变，只有字节变了），只重开读句柄、
  更新绑定/目录的指纹与树里的字节数。

**实测**（Linux 3.11.2；本机没有 Windows 标准编译器，故整包写回用合成包夹具验证，
24.5 MB 真包只做 I/O 计时）：全包重写 **0.07 s**，写后摘要核对 0.09 s，`.bak` 复制
0.01 s，`os.replace` 0.05 s —— 单次写回的 I/O 开销约 **0.2 s**，真正耗时在编译与审计。
单测 **462 项通过 / 121 跳过 / 0 失败**（新增 `test_inplace_build.py` 10 项、
`test_loose_save.py` 21 项），`ruff` 全绿。

**未验**：Windows 实机写回被测游戏占用的原包、真实双编译器下的端到端写回、Qt 交互观感
（悬停/对话框/红色模式按钮，本沙箱缺 `libGL.so.1`）、写回后的游戏内表现。
**未做**：写回后顺手把新指纹写进判定缓存（下次重开该包仍需 6.8 s 重扫）。

### dev12 的审查复核（PR #93，19 条 AI 意见）

去重 15 个问题，14 条属实已修、1 条驳回（要求取消宽松模式，与用户决策冲突）。与使用者
可见的行为变化只有三处，其余都是边界与诊断：

- **「没有内容变动」不再是错误**：源码与包内字节完全等价时（例如只改了注释、pyc 不变），
  写回不再弹「没有需要写回的改动」的错误框，而是保存 `.py`、状态栏说明，并**刷新这份源码
  的构建基线**，所以不会每次 `Ctrl+S` 都重新编译一遍。
- **64 条上限真的生效了**：以前这个检查藏在确认对话框的文案生成里，工作副本（客户端目录
  之外）的包因为跳过对话框而完全不受限；现在它在任何路径上都会先判一次。
- **写回前先关掉自己的读句柄**：Windows 上只要本进程还开着这个包，`os.replace` 就会共享
  冲突，看上去像「游戏占着文件」。现在写前释放、写完/失败都重开；真正的占用（游戏或别的
  查看器）仍给出「原包可能仍被打开，请关闭后重试；原包未被改动」。**这条只在 Linux 上验证
  过逻辑，Windows 实机仍待你验。**

- **一次写回不会把「没变的条目」变成永久候选**：同一批里若有条目编译后与包内字节完全等价，
  现在它们的构建基线也一起刷新；以前只有真正写进去的条目会刷新，剩下的会在**之后每次**
  `Ctrl+S` 里被重新编译、并继续算进 64 条上限。
- **悬停扫描从平方降到线性**：转义引号交给手写扫描器（`_literals`）而不是正则 body——
  同一段 16 KB 的 `aaa\'` 复读行，正则版要 **0.8 s**、扫描器 **2 ms**（200 KB 约 33 ms）。
  这不是理论问题：悬停一卡就是整个界面卡住。

其余修正：探针不再比全量更严（容差由 `MIN_ACCEPTED_RATIO` 推导）；缓存命中的
「按策略跳过 N 条」不再恒为 0；`raw_source` 用 8 MiB 源码预算（原 4 MiB 会否掉 worker
刚成功产出的 4–8 MiB 模块）；超时/超限/取消不再进会话缓存；字面量高亮与悬停对转义引号
一致，`\0`+八进制、`u''`、raw 串不再给假读法；`scan()` 会说明「分词提前停止」或
「达到 4096 条上限」，不再静默返回短列表；`.bak` 备份后复核摘要，不符就删掉这份没校验过
的副本并放弃覆盖。新增回归 21 项，单测 **482 项通过 / 121 跳过 / 0 失败**。

## 0.6.0.dev11：恢复稿里的 `\xNN` 现在能读了，但一个字节都没改

反编译器把 Python 2 的 `str` 常量按 latin-1 一个字节一个码位写出来，于是台服文案变成
`usermacro.PROMPT_MSG('\xa5u\xaf\xe0\xa8\xcf\xa5\xce...')`。**这些是字节串，不是
Unicode 文本**：客户端运行时按原始 MBCS 字节比较，把字面量换成中文就是改变语义，编译
出来的 pyc 也不再等价。所以本轮只加**显示层**，源码、项目文档、打包链路一个字节不动。

- **悬停预览**：鼠标停在这类字面量上给出可读文本，并在首行写明"只读预览 · 源码字节未改"。
  能读的字节串在编辑器里加**点线下划线**作为提示（仅样式，不改文本）。
- **编码 → 字节字面量 → 可读对照（只读）**：列出全文件每一处字面量的行号、原文与可读
  文本，可整段复制；对话框只读，没有保存/替换入口，报告也不含语句本身（不是"改写后的
  源码"）。
- **整串按字节解码，不是逐段猜**：`\xa5u` 里的 `u` 是字节 `0x75`，与前后 `\xNN` 同属一个
  字节流；先还原整串字节（Python 2 `str` 语义），再严格解码并要求**回编码得到完全相同的
  字节**，否则不给读法。`\n`、`\\`、`\u4e2d`、八进制转义、raw 字符串、已经含中文的字面量
  一律不声称可解码。
- **两种读法都列出，不替用户选**：`'combdialog/\xd4\xd3\xcd\xbc/\xcd\xac\xd2\xe2\xcc\xf5\xbf\xee.igs'`
  同时是合法 Big5 与合法 GBK：cp950 读作 `combdialog/娸芞/肮砩沭遴.igs`，gbk 读作
  `combdialog/杂图/同意条款.igs`。任何字节流都无法自证原作者用了哪个编码，所以顺序只是
  偏好（台服文案优先 cp950），报告里两种都写出来。
- 实现位于 `core/inspection/legacy_text.py`（纯函数、无 Qt，可单测）与
  `gui/literal_preview.py`（只读对话框）；新增 `tests/test_legacy_text.py` **27 项**。

**entry 4007 实测**（`script/login/register.py`，49,626 字符源码）：识别 **148 处**字面量、
分布在 **135 行**，全部为 cp950 可读；扫描耗时 **0.02 s**；报告 15,649 字符、未截断。
例如 `'\xa5u\xaf\xe0\xa8\xcf\xa5\xce\xbc\xc6\xa6r\xa9\xce\xa6r\xa5\xc0'` →
`'只能使用數字或字母'`；`'\xb5\xf9\xa5U\xb1b\xb8\xb9\xaaA...'` → `'註冊帳號服務條款頁-我同意'`。

**实测**：`ruff` 全绿；单元测试 **424 项通过、121 项跳过、0 失败**。
**未验**：真实 Qt 交互（悬停提示/对话框观感，本机缺 `libGL.so.1`）、Windows 实机、
把可读文本替换回源码后的客户端行为（本轮明确不做，见上）。

## 0.6.0.dev10：同一份证据不再重复计算，恢复长尾不再伪装成失败

本轮不新增功能，只把"同一件事被做了 2–6 次"和"0.08% 的条目决定全部体验"这两件
事修掉。**容器格式、密码学、护栏一条都没放宽**；固定扩展长度、未知 opcode、1288 策略
全部照旧。

- **参数表只读一次**：整包扫描原来逐条重读并重解析 426 KB 的授权参数表（实测
  `json.loads` 5.01 ms/条）。现在按 `(路径, 大小, mtime, inode)` 记忆化解析结果，
  **摘要仍然每次都从缓存的那份字节重算并核对**，文件一变立刻失效（`clear_catalog_cache()`
  可强制重读）。
- **native seed 表预计算**：`seed_from_keys` 原来对每条目录行重跑 640 步递推，现在一次性
  建好 32768 个 seed 的键序列表。实测 **两个 seed 真的会撞在同一个五键序列上**，所以
  歧义仍然拒绝（表里记 `None`），没有"取第一个"的退路。
- **包级判定缓存**（`core/services/verdict_cache.py`）：按 **包 SHA-256 + 参数表 SHA-256 +
  工具版本 + 排除策略** 寻址，只存"这套参数能不能解这个包"和随同产生的内嵌路径。

## 0.6.0.dev9：不再要求“先登记包指纹”

0.6.0.dev8 以前，编辑器只给**已登记的整套包指纹**自动套用五段 XOR 参数。用户每次
重新打一个包（哪怕只改了一条脚本），指纹就变，编辑器就认不出来，双击任何条目都只
提示“请先为此script包选择并确认XOR目录”。要求用户每次登记或手点目录，是产品缺陷。

新的判定顺序（打开包和打开项目都一样）：

1. 指纹已登记 → 直接套用（原路径，不增加任何耗时）；
2. 未登记 → 用随包附带的**唯一一份已授权参数表**对**每一条**允许的条目做严格解码
   （严格解压 → 原生边界校准 → 严格 marshal 解析）；
3. 解码成功率 ≥99% → 自动套用，并在信息栏写明“N 条逐条严格解码成功”，
   个别坏条目点名列出（例如 `条目 #4007：trailing/nonzero marshal data`），
   其余条目照常可开；
4. 成功率 <99% → 判定参数与包不匹配，**不套用**，报告失败条目与原因，
   包仍可浏览但文件名不发布。

这不是“猜密鑰”：参数只来自已授权的 `decoding/script-original.json`，变化的只是
“用到哪个包上”，而这个结论由 5001 条允许的条目独立严格解码给出（第 1288 条按策略
不读取负载，因此不计入）。手工“选择当前包的 XOR 目录”
同样先解码再询问，解不开就直接拒绝，不再问用户“你确认这是可信目录吗”。

真实回归：`data/script.fls`（r5）5001/5001 通过；r4（填充区按目录边界加密的旧包）
5000/5001 通过并精确点名 `#4007`。单条损坏的合成包也被点名而不是整包拒绝；
参数换一位后 0/5001 通过、整包拒绝。

## 当前具备什么

- 同时打开 `script.fls`（0SLF）和 `data.fls`（FLS\0）的只读索引，区分包来源、候选 VM、

- 显式将选中的**文字内容**转换为 Big5 文案或 GBK 路径的转义字节字面量；转换前预览确认。
  选择中不要包含引号/`u`前缀；不可编码直接报错，不替换丢字、不整文件转码。

## 内置双编译器

- `runtimes/py25/win-x86`：CPython 2.5.6，标准魔数`b3f20d0a`，用于script。
- `runtimes/py27/win-x86`：CPython 2.7.13，标准魔数`03f30d0a`，用于data。
- 每套包含真实x86 `python.exe`、对应DLL、ZIP_STORED纯Python标准库、5份许可与BUILD.json。
  schema2清单包含全部18个运行时文件的实际SHA256、官方源码URL/commit/归档SHA。
- 面向Windows 10/11，依赖操作系统UCRT和系统DLL，不支持XP/Win7；没有打包微软CRT或游戏DLL。
  是源码编译/marshal用途的最小运行时，不是含全部外部扩展的通用Python2发行版。
- 官方源码交叉构建，只有MinGW平台适配；compiler/opcode/marshal实现未改。
  `build_runtimes.py`供维护者从固定来源重建，不是普通启动或构建EXE的前置操作。
- 整套文件SHA/PE32/来源许可检查在注册、编译、回读前后复核；不回退系统Python/PATH。
  缺件/篡改/版本错误会禁用相应编译入口。Git不存放这些生成的二进制，完整源码交付ZIP中包含。

已完成真实PE构建及静态清单审计；**尚未在真实Windows执行，不宣称桌面/EXE/客户端验收通过。**
详见[运行时构建记录与剩余实机检查](M4_RUNTIME_DISTRIBUTION.md)。
