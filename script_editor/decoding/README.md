## 0.6.0.dev9：登记表降级为缓存，判定权交给逐条解码

只靠上面这张指纹表是不够的：任何一次重新打包都会改掉整包指纹，用户就得重新登记或
手点目录。dev9 起改为：

1. 指纹在表里 → 直接套用（不扫描，和以前一样快）；
2. 指纹不在表里 → 用本目录这份**唯一**参数表逐条严格解码
   （严格解压 → 原生边界校准 → 严格 marshal 解析，1288 按策略跳过）：
   - 成功率 ≥99% → 自动套用；个别解不开的条目**点名**列出，其余照常可开；
   - 成功率 <99% → 判定参数与包不匹配，不套用，并报告失败条目与原因。

参数自始至终只来自本文件，不按文件名/相邻目录/部分条目推定，也不估计边界或暴力
猜 key；“这份参数是否适用”由数据本身逐条证明。手工“选择当前包的 XOR 目录”同样
先解码再询问，解不开直接拒绝。

据此实测：本仓库 `data/script.fls`（`a45e0e49…`）5001/5001 通过；旧的 r4
（`9cf8c5cd…`，填充区按目录边界加密）5000/5001 通过并精确点名 `#4007`。

data.fls使用独立VM2.7流程，不需要此目录。

已登记测试派生包关联的是同一份已授权原表，仅允许逐条严格恢复尝试，不证明该包所有条目
都适用、不提升候选可信度、不修改参数/估计边界、不跳过native/marshal检查，不自动采用写包。
未拿到用户完整负载，不能声称实测其全部源码；若某条失败，应保留真实诊断而非猜key。

未登记的包不再一律拒绝：先逐条解码，再由成功率决定（见上）。若整包失败面过大，可先打开
它对应的 `.mxscript.json` 项目续编，或从菜单显式选择另一份已核实来源的参数文件，再逐模块
严格验证。未知映射或容量超限仍会拒绝，附带参数不代表全包每个条目都已支持。

`python -m script_editor.catalog_cli audit --root .`核对内置文件；Windows构建脚本
会复制到EXE旁`decoding`并复查，缺件/摘要不符/旧目标存在则阻断，不悄悄省略。
