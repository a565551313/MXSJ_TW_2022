# 哪些客户端表可以先整理成 CSV

## 结论与口径

本轮只读检查了 `script.fls` 的 **33个脚本条目、48个指定表目标**，其中38个目标可重建字面量赋值；10个未被当前读取器可靠重建。不是全客户端扫描，也没有生成正式CSV或进行繁简转换。

**目前可以开始制作保留来源的“待审CSV”，但没有哪张表因本轮检查就被认证为可直接投入服务端的正式规则。** 原生加载器验证仍未完成，原工具仍含启发式解码。下文“未标记”仅指通过本文实现的有限检查，不保证无其他错误。

本轮未应用前一轮的四个边界修复候选，所有计数均以原密钥库为基线。

## 1. 优先整理的辅助表

以下表中，已实现的编码、控制字符、相应字段类型检查没有标记异常记录，结构适合无损展开CSV。

| 客户端条目/表 | 当前条数 | 建议CSV字段 | 尚需注意 |
|---|---:|---|---|
| 1945 / `SHAPETABLE` | 4927 | client_shape_id, image_id | 图片资源是否存在尚未逐一验证；不是道具主表 |
| 1945 / `ITEMDATABYTYPE` | 6852 | client_shape_id, category_code | 键集合与道具主表一致，但分类编号的业务意义尚未全部确认 |
| 1945 / `EQUIPCONDITION` | 45 | client_shape_id, condition_1_raw, condition_2_raw | 条件是显示文本，不是服务端校验逻辑 |
| 3724 / `npcshapedata.DATA` | 50 | entry_key, shape_id, appearance_raw | 第二列数据后的造型参数字符串保留原样，不擅自解释六个数字；不是完整NPC坐标表 |
| 960 / `summontalentdata.DATA` | 76 | talent_id, iNeedServerGrade, iSort | `iRelatedList`另表展开，保留顺序；相关技能引用尚未闭合 |
| 3515 / `ROLEDCT` | 6 | shape_id, name, sex | `lpList`另表展开；角色到本文件门派表引用可闭合 |

图片映射比道具表少，并不表示每个缺项都是错误：客户端 `Shape2Image` 在未查到映射时会回退到原shape。本次统计2235个道具无显式映射、310个映射键不在道具主表，不应盲目删掉或强制补齐。

这些表适合先保留原ID和原字段，生成待审版本和异常清单。未标记条数不等于确认正确的正式配置数量，也不表示这些记录全部在正式游戏中开放。

### 新发现：宠物资质并不是没有，而是在另一张表

`script/data/petaptitudedata.py`（2954）的132条记录，每条包含十个整数：法力、防御、攻击、速度、体力五项资质，以及各自名为“最大值”的字段。

132个键都能在135条宠物详细表中找到；详细表中的3010、4021、4022没有对应资质记录。不要把缺项当作零，也不要猜测“资质”和“最大值”的精确游戏计算意义。

例如毛草團2010：原字段“攻擊資質”为1660、“攻擊資質最大值”为1942。这些是客户端表值，不是本轮推导出的服务端成长公式。

### 宠物技能要拆子表

`maySkillLst`在当前marshal重建中实际是tuple（序列），内容是技能名称，不是ID；JSON预览会把tuple显示成数组。建议未来拆成：

```text
pets.csv: client_shape_id,name,liupai,attack_type,carry_grade,maxskillnum,address_raw
pet_skill_candidates.csv: client_shape_id,sequence,skill_name_raw
pet_required_skills.csv: client_shape_id,skill_name_raw
pet_aptitudes.csv: client_shape_id,五项原资质值,五项原最大值
```

先保留原文与顺序，不在宠物技能主表未恢复时擅自生成skill_id。`maxskillnum`也先保留原名，不推定其在所有培养阶段的规则含义。

## 3. 暂不作为可信主配置导出

- **宠物技能主表3205、人物技能主表454、技能书3075**：目标赋值未被现有受限读取器可靠重建。需要解决解码/转译/字面量解析问题；“读取器失败”不等于客户端不存在这些数据。
- **宠物主动技能2242**：48项中的64605仍是未确认候选问题；本轮没有擅自改为416。
- **商城2409**：14条中，8号记录的 `itemid`为文字“雙技能英靈護符”；7、9号商品引用也未在当前道具主表中找到。价格、类型含义及是否为历史活动仍需核查，不可直接用作服务端商城。
- **烹饪1381、药品类型2338、装备图标293、NPC坐标2601/2804、家具主数据244、另一份道具表4924**：读取器未可靠恢复指定目标。不执行脚本来绕过限制，不补造数据。
- **mxpetdata1115**：137条映射中2910值类型异常；还有与详细表的用途/名称差异，不能直接替换宠物详细表。
- **道具扩展说明1698**：不仅有编码失败，还发现控制字符；27条中本轮标记10004、10020、10026三条。不能只排除10004就说剩余均正确。

另有宠物图鉴、怪物说明、称谓、Buff说明等表已经获得结构统计，但仍有文字异常或没有完整字段/业务语义验证。当前 `monsterdata` 样例是含图鉴说明的资料，不可据文件名当作完整怪物战斗属性表。详见机器报告，不把“零编码错误”包装成“全部可靠”。

## 复现与实际检查范围

```bash
PYTHONDONTWRITEBYTECODE=1 python3 server/tools/survey_csv_readiness.py
PYTHONDONTWRITEBYTECODE=1 python3 -m unittest discover -s server/tests/architecture -v
```

机器结果：[`catalog/csv_readiness_survey.json`](catalog/csv_readiness_survey.json)。工具仅使用标准库及仓库已有解析器，记录输入散列、实际脚本名、指定表目标、失败原因、样例、逐条问题及交叉引用结果。

与前一轮相比，本轮识别 `STORE_NAME` 和 `STORE_GLOBAL` 两种顶层赋值；仍只允许字面量构造，不执行函数、导入或运行时表达式。也不声称重建了脚本执行后可能再次修改的最终表值。

检查包含：严格CP950、嵌套控制字符、重复键拒绝、部分表的明确字段类型、部分表间ID/名称比较，以及资质与其命名“最大值”的一致性提示。每张表的 `schema_checked` 标记说明是否实现了专门的字段类型检查；未实现时不能借其他表的检查冒充完整覆盖。

最终建议：**先做辅助表及隔离异常后的道具、宠物、资质待审CSV；不要先拿商城价格、技能规则、掉落或战斗数值直接搭正式服务端。** 本轮没有生成CSV，也没有修改客户端、历史解码库或正式配置。
