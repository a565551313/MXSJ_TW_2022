# 可拆分多功能网关与会话路由设计 v0.2

> **状态入口**：本文是正式服务端的设计约束，不是根目录 Mock 的实现说明。当前实现／测试边界见 [STATUS](../../docs/STATUS.md)，最小链路与验收顺序见 [ROADMAP](../../docs/ROADMAP.md)。本轮没有新增运行接口、数据库或网络服务。

日期：2026-10-12。状态：**设计约束已纳入开发基线，运行实现尚未交付**。
这是新服务端的设计，不声称还原原服架构或已兼容原客户端报文。

配套设计：[安全防护与 GM 控制面](GATEWAY_SECURITY_GM.md)。网关产品同时规划连接接入、安全防护和 GM 管理入口；
公网游戏入口、私有管理入口与内部服务入口严格隔离，管理业务不在连接层执行。

## 1. 决策与范围

- 第一版采用 **Python 同进程、模块化接入**；预留独立网关，不先引入微服务集群。
- 多功能网关包含安全策略执行、风险告警和独立 GM 入口。GM 写操作走 administration 与业务端口，
  不提供 SQL/shell/任意脚本，也不在玩家监听上注册管理命令；生产管理入口私有化、默认关闭。
- 业务依赖类型化命令、受信任的 RequestContext 和返回 DTO，不依赖 socket、网关节点或连接生命周期。
- 拆网关时替换投递/回送适配器与装配，不修改玩法规则；内部通信和故障处理仍需实现、测试，不能宣称零成本拆分。
- 不把当前 FastAPI 只读复核 API 改成游戏网关。复核工具与游戏接入是两条独立链路。
- 本轮不选定 RPC 框架、消息中间件、服务发现产品，不新增生产依赖、数据库表或客户端改动。

第一版：

```text
客户端 → transport（连接/帧）→ protocol（白名单适配）
                                  ↓
         runtime（会话校验 → 归属路由 → 有界投递）
                                  ↓
         modules（应用服务 → 状态拥有者/规则 → 持久化）
                                  ↓
         类型化结果/定向通知 → 回送适配 → protocol → transport
```

后续独立部署：

```text
客户端 → 网关进程 transport + protocol + 接入限流
                  ↕ 经服务身份认证的内部通信适配
         业务进程 runtime + modules + persistence
                  ↕ 会话权威/实例归属目录
```

业务进程不暴露给公网。客户端外部协议与内部消息协议独立版本化；只拆网关不应迫使客户端同步升级。

## 2. 职责与安全边界

| 部分 | 负责 | 不负责 |
|---|---|---|
| transport / 网关连接层 | 握手阶段、拆包粘包、长度限制、连接心跳、发送队列、连接级限流 | 角色属性、战斗规则、资产读写 |
| protocol | opcode 白名单、字段转换、旧编码边界、业务结果映射为客户端报文 | 接受客户端指定 Python 方法、目标节点或可信身份 |
| runtime 会话层 | 票据验证/撤销、绑定连接、会话接管、当前代数校验 | 用 source=client/admin 替代业务授权 |
| runtime 路由层 | 解析实体归属、校验归属代数、向唯一拥有者投递、回送定位 | 按任意客户端地址转发、自动创造第二个状态拥有者 |
| 业务应用/状态拥有者 | 角色归属、可操作单位、回合阶段、资源、实体版本、幂等和提交保证 | 保存 StreamWriter、直接调用 socket.send、指定网关 IP |
| persistence | 事务、唯一约束、持久化幂等结果、必要的会话 fencing | 与一个连接共享长期数据库事务 |
| 安全策略执行 | 多维限流、畸形包拦截、已批准策略版本应用、风险事件 | 独自判定全部外挂、替代上游抗 DDoS、因弱信号自动永久封号 |
| 私有 GM 入口 | 员工认证/MFA、权限初检、请求适配、审计关联 | 复用玩家票据、信任自报 source=admin、直接改库或在线对象 |
| administration | 二次授权、审批、管理任务、审计、调用业务端口 | 绕过业务事务、通用 SQL/脚本执行、自我审批高风险操作 |

登录前仅开放握手、认证等白名单请求，限制长度和频率；认证失败不能产生已登录上下文。
账号认证服务验证凭据并签发票据，网关/会话层不能凭客户端 account_id 自行认证。
票据须绑定区服/用途、过期时间及撤销状态，禁止日志记录凭据和原始票据。
内部请求须有服务身份认证和传输保护；验证允许的调用者和消息类型，内网位置本身不是信任依据。

## 3. 四种身份不能混用

| 身份 | 含义与寿命 |
|---|---|
| connection_id | 一次连接的传输句柄；重连更换，不作为角色或幂等键 |
| session_id + session_epoch | 一次授权会话及接管代数；由会话权威生成，业务执行入口验证 |
| realm_id + character_id / battle_id | 业务身份；不随连接或网关更换 |
| owner_id + owner_epoch | 实体所在业务实例及归属代数；与 session_epoch 不同 |

第一版会话接管范围定为 `(realm_id, account_id)`：同一区服同一账号仅一个活动客户端会话，
一个会话同时仅绑定一个已选角色。角色列表阶段 character_id 可空；选角必须核对账号归属。
这是一项新设计，不是对原版多开规则的断言；以后允许多会话必须显式调整范围与测试。

同进程中会话注册表是唯一运行期权威；恢复时从持久化代数/撤销状态重建，不能重启归零后重新接受旧票据。
拆分后仍须保证同一接管范围的权威操作串行/原子化，不能每台网关独立递增计数。

## 4. 接管、失联和恢复

1. 新连接先完成认证或票据验证，不能凭 connection_id、账号 ID 或旧 session_epoch 直接恢复。
2. 会话权威串行推进 session_epoch，撤销旧绑定；向受影响的状态拥有者安装新的 fencing 代数。
3. 接管与角色命令接受在同一拥有者上形成确定顺序；新代数生效后才确认接管成功并允许新连接提交。
4. 旧连接、旧队列消息和迟到的旧关闭通知必须携带代数校验；旧关闭通知不能删除新绑定。
5. 已在接管之前合法接受的命令可能继续完成，不承诺撤销已提交事务。需要禁止跨接管提交的操作，
   必须在持久化提交路径做 fencing/条件更新，不能只在网关接收时检查一次。
6. 重连取得授权后的角色/战斗当前视图及必要的版本，不无条件重放所有历史推送。

网关故障通常会断开其客户端 TCP 连接；保证目标是可重新认证并恢复业务状态，**不是 TCP 无感迁移**。
掉线不删除角色、不直接结束战斗；离线托管与超时行动由战斗拥有者决定。
会话权威不可用时不能猜测代数、接受接管或放行未经确认的客户端写命令；已接受的战斗回合可按规则推进。

## 5. 内部投递与回送契约（待实现签名）

下列是需要实现并做契约测试的端口，不是现有 Python Protocol；具体载荷联合评审后再写入 `contracts/`。

| 端口 | 责任与结果 |
|---|---|
| SessionAuthority.authenticate / resume / bind_character / revoke | 授权会话绑定与代数；原子接管，不泄漏原始凭据 |
| OwnerDirectory.resolve | 服务端根据授权实体身份取得路由及 owner_epoch；不接受客户端选择节点 |
| CommandDispatcher.dispatch | 接收类型化命令与可信上下文，投递给拥有者；返回明确回执或执行状态 |
| ClientDelivery.reply | 按请求回送句柄回包，校验该连接仍绑定相同会话代数；失联不撤销业务提交 |
| ClientDelivery.notify | 接收业务已授权的接收者和视图，解析当前有效连接；不让业务维护连接列表 |

`bootstrap` 注入进程内实现；拆分时注入远程适配器。业务返回值、事件与纯规则不变。
接入与业务两侧都必须做运行时类型/大小校验；dataclass 冻结不等于不可信消息已验证。

### 5.1 内部信封字段

- `message_type`、`schema_version`：注册白名单与兼容版本；禁止动态 import、eval 或反序列化 pickle。
- `request_id`：单次请求/响应关联，不是业务幂等保证。
- `RequestContext`：复用已有 operation_id、trace_id、realm_id、account_id、character_id、session_epoch、source。
- `session_id`、不透明回送句柄：放在接入信封，由受信任的运行时使用，不扩散到玩法参数。
- `target_kind`、`target_id`、`owner_epoch`：授权后由服务端解析/验证；战斗 ID 仍须校验参与关系。
- `remaining_budget_ms`：有限的剩余等待预算；入口限制上限，各跳扣除耗时，禁止跨进程传单调时钟时间戳。
- `payload`：对应消息类型的明确 DTO，只含可序列化值，不传连接、ORM 会话、Python 异常或可变业务对象。

结果区分成功、明确拒绝、未知执行结果；响应按 request_id 关联，不假定 TCP 顺序等于业务完成顺序。
业务事件按实体 revision/事件序号判断重复和缺口，不承诺跨角色/跨战斗全局顺序。

### 5.2 请求 ID、幂等键与未知结果

- operation_id 的有效命名空间包含业务操作类型和授权主体；同键不同参数必须拒绝，不能读取别人的结果。
- 客户端重试同一业务操作必须保留稳定幂等键。旧协议没有此能力时，需明确改客户端或设计可验证的映射；
  网关每次收到报文生成新 UUID 不能防止重连后重复扣款。
- 网关、路由和内部通信默认不自动重试有副作用的命令。业务层以持久化幂等结果支持安全重试。
- 超时只表示等待结束，不表示操作回滚；已经投递但无法确认结果时返回/记录未知状态，用原 operation_id 查询。
- 请求在真正开始执行前已过期可拒绝；执行中取消不推定数据库提交被撤销。
- TCP ACK、进入网关队列、进入拥有者队列，都不是持久化业务成功；遵循 INTERFACES.md 的回执语义。
- 不承诺网络 exactly-once；依靠持久化幂等、唯一约束、状态版本与适当重试实现业务效果去重。

## 6. 路由、单写者与背压

第一版 OwnerDirectory 可为同进程注册表，角色/场景/战斗分别串行处理自有状态。
角色进入战斗后，战斗命令按 battle_id 路由到战斗拥有者；世界与战斗的所有权交接遵循 BATTLE.md。
不能把连接所在网关当角色或战斗的拥有者，不能跨实例传可变角色对象。

拆分后过期 owner_epoch 必须拒绝。只有明确“未接受执行”的路由失败才能刷新路由后重投；
其余情况视为结果未知，按幂等结果恢复。拥有者故障不允许仅刷新地址就创建第二份状态。
实例转移需停接收/栅栏、快照恢复、原子归属切换；未实现前不开放在线迁移。

每连接输入/输出队列、每拥有者 mailbox、每调用者在途请求均有明确上限。
满载时明确拒绝或断开慢连接，不无限排队；持续性限流也应在会话/业务层执行，防止重连绕过。
可丢弃/合并的瞬态通知必须有类型白名单（如允许的最新位置视图），不得任意丢弃战报或资产回执。
可靠通知发不出去时保留业务结果并提供重查/重同步，不要求依靠网关内存永久缓存全部历史。
第一版实现前须选定并测试帧大小、队列容量、并发数、等待预算和停机期限；本设计不虚构容量数据。

## 7. 目录所有权与实施次序

| 路径 | 所有者 | 本阶段边界 |
|---|---|---|
| `contracts/`、本设计、INTERFACES.md | 集成负责人 | 统一信封、错误分类与 DTO；接入/运行时/调用方联合评审 |
| `transport/`、`protocol/` | 接入负责人 | 帧、协议映射、回送；不实现玩法授权或存储 |
| `runtime/` | 基础设施负责人 | 会话、单写者、路由、投递、超时与队列生命周期 |
| `bootstrap/` | 基础设施负责人 | 同进程装配；后续更换远程适配器 |
| `persistence/`、`migrations/` | 基础设施 + 数据库集成负责人 | 会话 fencing、幂等与恢复相关持久化边界 |
| `modules/<name>/` | 模块负责人 | 业务权限、规则与事务；不导入接入/协议实现 |
| `tests/protocol/`、`tests/integration/` | 接入/基础设施 + 独立验收 | 报文、会话并发、投递失败和真实数据库验证 |

实施次序：

1. 核查客户端登录→选角→进图链路；确定外部请求关联/幂等键和必要客户端改动。
2. 冻结会话/消息/回送端口及错误模型，实现同进程适配器、认证和真实数据库最小闭环。
3. 单进程阶段即验证序列化边界、有限队列、超时与断线；fake 只能证明契约，不宣称远程通信已完成。
4. 有独立扩缩容或故障隔离需求时，再实现服务身份、内部通信、权威路由与故障恢复。
5. 远程适配器通过相同业务契约测试和新增网络故障测试后，才宣布支持独立网关部署。

优雅停机：停止接入/接管新请求，限时排空已接受请求；未确认结果保留查询路径，
会话绑定按代数失效；业务拥有者保存其恢复所需状态。网关停机不直接销毁战斗实例。

## 8. 必须进入下一阶段验收的用例（当前均未实现）

| 用例 | 预期 |
|---|---|
| 伪造身份/区服/管理员来源或目标节点 | 接入或业务授权拒绝，无越权数据 |
| 两连接并发接管、旧关闭通知晚到 | 仅当前代数有效，新绑定不被旧通知删除 |
| 旧代数命令已在队列中 | 在业务接受边界拒绝；接管前已接受命令按明确提交规则处理 |
| 同角色两场战斗、战斗中掉线 | 所有权不冲突；掉线不删除战斗，重连返回授权视图 |
| 重复请求、同键不同参数、跨账号复用键 | 不重复副作用、不误复用结果、不跨主体泄漏 |
| 提交成功但回包丢失 / 提交结果未知 | 原 operation_id 可恢复结果，不盲目再次扣款 |
| mailbox 满、慢连接、内部超时 | 队列与内存受限，明确错误，不伪成功、不擅自重试 |
| 旧 owner_epoch / 路由目标故障 | 不产生第二个写入者，不把未知执行误判未执行 |
| 网关重启 / 会话权威不可用 | 连接可重建，旧票据不因计数归零复活；未知授权写请求拒绝 |
| 通知重复/乱序/缺口 | 按实体版本处理或重同步，不依赖全局顺序 |
| 内部身份错误、未知消息类型/版本、超大载荷 | 边界拒绝，不动态执行载荷 |
| 同进程与远程适配器替换 | 业务契约和幂等/授权语义相同；远程场景另测分区、重连与故障 |

本设计不改变首批复核 CSV、参数、原始归档、客户端或正式 game_data，也不代表上述用例已通过。

## 9. 安全与 GM 扩展基线

详细功能、权限矩阵、审批/审计链路与分期见 [GATEWAY_SECURITY_GM.md](GATEWAY_SECURITY_GM.md)。
安全基础随第一条登录闭环实现；GM 只有在独立身份、权限、审计和网络隔离就绪后才能启用。
最小 GM 先做脱敏查询、会话撤销和受限处罚；补偿、维护、配置与角色救援按对应业务就绪情况开放。
现有 source=admin 和 AdministrationAPI 草案不构成管理端安全实现，管理员上下文须单独联合冻结。
玩家业务与 GM 操作共用可靠执行原则，但身份、权限、审批、资源预算和审计要求不能混同。
