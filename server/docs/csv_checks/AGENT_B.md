## 2. 方法与复现

只读，不执行任何恢复脚本，不 `exec`/`import` 游戏代码。

复现（在仓库根目录）：

```bash
PYTHONDONTWRITEBYTECODE=1 python3 server/tools/agent_b_item_probe.py \
  --out server/docs/csv_checks/agent_b_probe.json     # 约 14 秒，输出确定性
PYTHONDONTWRITEBYTECODE=1 python3 -m unittest discover -s server/tests/architecture -v   # 31 项通过
```

查看某条记录的证据：

```bash
python3 -c "import json;d=json.load(open('server/docs/csv_checks/agent_b_probe.json'));print(json.dumps(d['records']['1945/DATA/71700'],ensure_ascii=False,indent=1))"
```

方法要点：

1. **字节层**：payload 由 `review_client_data_boundaries.Review.payload` 取得；解码为 `decoded[p] = payload[p] ^ key(segment(p))`，段边界取自密钥库 `bounds`。每条异常记录 payload 偏移、所在段、段密钥、原始字节、解码字节。
2. **读取层**：整表通过 `Review.load` + `extract_table`（不支持时回退 `survey_csv_readiness.extract`）。与已知读取器一致。
3. **候选检验**：只对候选边界做“本地探测”。同时看三件事：严格 CP950 有效性、文字是否通顺（不转繁简）、整表是否可解析与受影响行。单靠 CP950 有效性不能区分候选（多个位移都能通过），因此每个候选都附带交叉表/副本一致性证据。
4. **交叉副本**：同一 FLS 中 1945（名称+描述）、1182、4924（名称）是按不同密钥/边界编译的同一道具名称表的副本，可作为独立证据（但仍不是权威来源）。

## 3. 分类定义

- **解混淆/转译错误**：字节的解码或段边界错误，有证据指向正确的字节解释。
- **读取器不支持的合法表达式**：字节解码正确、表达式合法，但读取器拒绝。本轮未找到确证的此类记录；1381 的 `BINARY_DIVIDE` 被怀疑是边界错误，需 A 确认（§4.3）。
- **客户端原始值**：解码正确、字节在多个副本中一致，但内容可能在客户端显示异常。
- **合法名称差异**：两份来源都合法、只是名字不同。本轮未能证明“合法”，因此多数名称差异标为“仍未解决（保留两份）”。
- **仍未解决**：证据不足，不能判定。

状态：`可待审`（不含候选修正）、`隔离`（不得进入待审 CSV）、`候选`（有待 A 原生验证的边界证据）、`保留`（保留两份名称）。

### 4.12 其他需要注意的通用问题

1. **PY25_MAP 静默回退**：`transpile_py25_code` 中 `PY25_MAP.get(op, 9)` 把未知码替换为 NOP，且不报错。这会把错误“静默”地变成数据丢失/错位。建议 A 改为显式报错或计数。
2. **读取器指令游走错位**：NOP 与真实码的参数长度不一致时，后续指令全部错位。报错位置可能远离真实缺陷（如 293 的 co 1000 vs co 1003）。判断前必须先排除该因素。
3. **solver 干扰**：solver 会改写 payload（1381 的 2521–2524）并重算边界，因此 solver 路径的结果不能独立验证候选边界。
