# 回环测试计划与假设（2026-10-10）

状态：**假设，未验证**。依据为 E-LOOPBACK-001/002/003、E-IDA-DYN-004，以及 `notes/co_code_analysis/任务A深入-Connect函数破解报告.md`（该报告基于 v4 映射，文档本身提示需用 v4.3 重审）。

## 已知事实
1. 客户端能连上 `127.0.0.1:3134`（E-LOOPBACK-002：Get-NetTCPConnection 显示 Established）。
2. 连接后，客户端 10-09 的 22 次测试与 10-10 本次测试均未发出任何应用层字节（捕获文件 0 字节）。
3. 服务端发送 `00 02` 后，客户端在 `KernelBase.dll!RaiseException` 处异常（E-IDA-DYN-004）。说明客户端**确实会读取并解析收到的数据**。
4. 脚本中的 `Connect()` 对每个 IP 先 `NakedSend(chr(port & 0xFF))`，再 `Connect(ip, port)`。3134 的低字节为 `0x3E`。若该字节在 Winsock 连接完成前发出，可能被原生层丢弃（该段落来自 v4 反汇编，待 v4.3 复核）。
5. 脚本存在 `PROXY_CONNECT_TIMEOUT` 与 `nexttest`：超时后会切换到下一个候选。

## 假设（按可检验性排序）
| 编号 | 假设 | 支持 | 反对 | 检验方法 |
|---|---|---|---|---|
| H1 | 客户端在收到服务端数据后才发送 loginhello（服务端先发） | 客户端会解析收到的数据（事实 3） | 没有已知的服务端首包格式 | 需要可被客户端接受的首包，不能靠猜；风险：`00 02` 已导致异常 |

| H3 | 连接前的 `NakedSend` 单字节被丢弃，导致客户端认为握手未开始 | 脚本中有该调用 | 反汇编来自 v4 映射，未复核 | 在 Winsock `send` 调用前后观察字节（需调试或 IDA 动态） |

依据：`notes/parallel-20261010/P1-result.md` 至 `P4-result.md`（PR #6–#9，已合并）。以下只记录状态变化，旧表保留不改。

| 假设 | 更新后状态 | 依据 |

| H3 NakedSend 单字节被丢弃 | **前提不成立，建议作废或改写** | P3 §3.2、§4：直连分支没有连接前的 NakedSend；`NakedSend` 只在代理分支、`Connect(代理)` 之后发送 8 字节（4 个 IP 八位组 + 4 字节小端端口，3134 为 `3E 0C 00 00`）。原“单字节 0x3E”是误读。 |
| H4 IP 拆分错误 | **不成立，建议作废** | P3 §3.3：分隔符为 `'.'`，`127.0.0.1` 切分正确，且切分结果不用于候选选择。 |
| H5 登录走其他通道 | 未检验 | 需要运行时记录全部 TCP 连接，不在静态分析范围内。 |

**对我们问题的含义（推断，未证实）**
- 直连分支在连接后本身不发字节。这样 0 字节捕获与“直连 + 等待某个事件后才发”相容。
- 如果测试实际走的是代理分支，理论上连接后会先发 8 字节。但 P3 指出 `Connect` 可能是异步的，因此这一点不能直接用来否定代理分支，需要运行时确认。
- **需要确认的是：测试时客户端走的是直连还是代理分支**，这取决于代理列表与 `g_AutoProxy` 等配置（未证实）。下一次测试应同时记录这一点。
- 因此，下一步不是猜第一包，而是（a）用观察器确认 `ws2_32.connect` 的目标地址和端口，以及之后是否有 `send`；（b）确认分支选择。
