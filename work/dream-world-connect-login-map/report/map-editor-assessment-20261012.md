# 地图编辑器 — 现有工具评估报告（2026-10-12）

**角色**：客户端总指挥
**目的**：第一期目标是地图编辑器。本文先把现有地图工具的实际能力核清楚，说明哪些能复用、哪些是硬阻塞。
**方法**：每个工具都实际运行过；格式结论都从 `map/*.map` 原始字节和 `mx.exe` 反汇编独立复核，不采信既有文档。

---

## 0. 一句话结论

**现有 6 个地图工具全部是只读查看器，零写入能力。** 对编辑器而言，可复用的只有格式解析层（这一层质量不错，可以直接当地基）。编辑器本身要从零建，且有 **3 个硬阻塞**必须先解，其中 1 个是格式未知、2 个是缺编码器/跨数据源。

## 2. 格式复核：我独立验证过的部分

五份样本 `2101 / 2111 / 2112 / 2122 / 2303`，共 245 个分块：

| 检查项 | 结果 |
|---|---|
| 头部魔数 `0.1M` + `2000` + `1500` + 49 个绝对偏移 | ✅ 五份一致 |
| 每块 `GEPJ` / `LLEC(192)` / `GIRB(22)` 三段标记与长度字段 | ✅ **0/245 失败** |
| 分块长度恒等式 `246 + 4r + L`（`r`=记录引用数） | ✅ **0/248 失败** |
| `GIRB` 体是否恒定 | ✅ **245/245 完全相同**：`02888888888820000000000000000000430000110000` + 尾 `00000000` |
| GEPJ 分段表形态 | 86 种；160 块是 `头段281 + 12×76` 等长形态，其余各不同（最大总长 15328） |
| `2303` 前置记录 | 32 条，五字段 = (x, y, w, h, payload_len)，`总长 = 20 + payload_len` |

**对写回器最有价值的两点**：GIRB 恒定（直接照抄，不必理解）；偏移表是**绝对文件偏移**，所以改任何一块的体积都要重算后续全部偏移——这是写回器的主要工程量，也是必须先有"无损往返"测试的原因。

## 3. 新发现：LLEC 与原生寻路代码对上了（但只对上了一半）

`notes/task-c-地图分析/artifacts/native-walkable-disasm.txt` 里有三段关键反汇编，本轮复核如下：

- `mx.exe:0x4baebf` —— 用 `imul 0x66666667` + `sar 3` 做**有符号除以 20**：像素坐标 → 格坐标，**每格 20×20 像素**。
- `mx.exe:0x4bbb00` —— `movzx ecx, WORD PTR [edx]`（网格宽，u16）、`cmp WORD PTR [eax+ecx*2], di` / `jae` → 返回 0，否则返回 1。即 **网格元素是 uint16，判定条件是 `grid[y*w+x] < threshold`**。
- `mx.exe:0x4b8d3c` —— `mov eax,[eax+0x50]; add eax,0xC0`（0xC0 = **192**），与 LLEC 的 192 字节长度字段吻合。

由此得到一条**之前没人做过的恒等式**：

```
7×7 分块 × 16×12 格      = 9408 格
49 × 192 字节(LLEC)      = 9408 字节   ← 完全相等
分块覆盖 2240×1680 px ÷ 20 = 112×84 = 9408 格
逻辑图 2000×1500 px ÷ 20   = 100×75 格（裁切后）
```

**结论：LLEC 确实是 20×20 像素一格、每格 1 字节的网格**，7×7 分块铺满 112×84 后裁切到 100×75。这条把 LLEC 的几何定义钉死了。

### 但语义仍未定，而且现有解释很可能不完整

我扫了全部 5 图 47040 个格子：

- **480 个格子（1.020%）不是 0/1**，值域散布到 255，共出现 **88 种不同取值**（其中 86 种 >1）。
- 它们**成连续多字节段**出现，不是孤立点：
  - `2112.map` sector 13：异常在索引 **40 / 88 / 136 / 184** —— 按 16 列折算全是**第 8 列，行 2/5/8/11**。
  - `2112.map` sector 27 / 34 / 41：**第 5 列和第 8 列，每一行都有**，每处 2 字节（`d51a`、`696e`）。
  - `2112.map` sector 6：`a0c1ec06` / `c8d97b04` / `28db7b04` / `50148004`，位置 12/40/88/136。
- **按列统计高度偏斜**：列 5/6/8/9/10/11 分别有 62/59/84/88/53/42 个，而列 0-4、12-15 只有 2~12 个；**按行统计大致均匀**（29~59）。

纯"每格一个可行走标志"的模型**解释不了这种列聚集结构**。另外原生网格是 **uint16**、LLEC 是 **1 字节**，中间必然存在一次变换（阈值映射？另有一份数据？），现有工具完全没有触及。

> **对编辑器的直接含义**：在搞清这 1% 的字节含义和 u8→u16 变换之前，**不能开放可行走层编辑**。让用户涂格子然后保存，等于往客户端寻路网格里写垃圾。现有 `map_viewer.py --overlay-cells` 的帮助文本自己写着 "semantics unconfirmed"，`map-format-analysis.md` 也写着"不要把网格图当成已证实的碰撞图"——这个自我限制是对的，必须继承。

## 4. 三个硬阻塞

### 阻塞 1：没有 GEPJ 编码器 → 改不了贴图

`gepj_decoder.py` 只有解码方向。它做的事是：从共享 JPEG 头去掉 `FF A0`、把 `SOS` 长度 `0009` 改成 `000C` 并补 `00 3F 00`、对 12 段各自做 `FF → FF 00` 填充并补 `FF D9`、用 `convert` 解出 12 张 80×80、拼 4 列×3 行成 320×240、再 7×7 拼成 2000×1500。

反向需要能生成"**无 SOI、SOS 长度被写成 0009、分量选择符后不带 `00 3F 00`、扫描流中 `FF` 不做填充**"的裸段。而且分段表有 **86 种形态**、长度随内容变化，不能复用固定模板。这是编辑器里工作量最大的一块，且需要 ImageMagick/libjpeg 的底层控制。

### 阻塞 2：LLEC 语义未知（见 §3）

可行走层是地图编辑器最核心的可编辑对象，现在恰恰是它不能碰。

### 阻塞 3：NPC / 传送点 / 刷怪点不在 `.map` 里

这点必须先说清楚，否则方向会做错：

- `.map` 里只有 GEPJ 图像、LLEC 网格、恒定的 GIRB 尾块，以及（仅 `2303`）32 条空间对象记录。
- 那 32 条记录实测：`rec0=(1159,1205,60,33,171)`、`rec1=(1219,878,61,327,396)`、`rec2=(1600,708,100,541,968)` —— 前四字段是矩形、第五是载荷长度，载荷首 6 字节都是 `02 00 00 00 00 00`。**具体是什么对象仍未确定**，原文档明确写了"不能直接命名为 NPC/传送点"。
- 真正的 NPC 坐标在 `script.fls`：`npcposdata`（1335 条记录，已在 `server/docs/csv_checks/batch_001/maps_npcs/npcposdata_records.csv`）、`minimapnpcpos`、`sceneid2name`、`mapdata_scene_dictionary` 等。

**所以地图编辑器天然是跨数据源的**：`.map` 二进制 + `script.fls` 条目（走我们已经建好的 FLS 解码链，`tools/fls_batch_decoder.py` 实测可用）。这也意味着编辑器需要一个统一的场景 ID 映射层。

## 5. 可直接复用的资产（好消息）

1. **格式解析层可靠**：245 块结构校验 0 失败、长度恒等式 0 失败。`map_parser.py` 的 JSON 输出字段齐全（header / grid / sectors[].image.segment_lengths_u16_le / cells / prefix_records）。
2. **GIRB 恒定** → 写回时照抄，无需理解。
3. **PNG 输出是纯标准库**（自己拼 IHDR/IDAT/IEND + zlib），不依赖 Pillow。这条路在本环境验证可用。
4. **两套测试（11 + 7）当前全绿**，可以当编辑器的回归基线。
5. **LLEC 几何定义已钉死**（20px/格、112×84 裁到 100×75），这是 §3 的新成果。

## 6. 建议的推进顺序（待确认后执行）

`parse → 原样重打包 → 与原文件逐字节比对必须完全一致`。这是编辑器的地基，同时是对格式理解的 100% 证明。GIRB 恒定 + 长度恒等式已知，让这一步很轻。产出：`map_writer.py` + 往返测试。
