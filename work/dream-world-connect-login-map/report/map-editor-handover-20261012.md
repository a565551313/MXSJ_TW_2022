## 4. `.map` 格式（已确证，8 张样本 + 101 张真实地图交叉验证）

### 文件头

```
0x00  "0.1M"                    魔数
0x04  u32 width
0x08  u32 height
0x0C  N × u32                   各扇区绝对偏移（严格递增）
      u32                       自指哨兵 = 12 + 4N + 4
      u32                       前缀记录数 R
      R × u32                   各记录绝对偏移
```

**扇区数 `N = ceil(W/320) × ceil(H/240)`**，已在 49 / 195 / 234 / 800 等
多种扇区数上确证。**不要硬编码 49。**

### 扇区结构

```
u32 ref_count | ref_count × u32
"GEPJ" u32 len | 26 字节头（13 × u16 段长）| 载荷
"LLEC" u32 192 | 192 字节
[GIRB] u32 len | len 字节 | 4 字节尾
```

`sector_len = 246 + 4×ref_count + GEPJ_len`。

**解析器是「按 tag 通用走位」**：遇到不认识的 tag 就存进 `extra_blocks` 继续走，
`GIRB` 作为终止符。**不要退回硬编码 `GEPJ→LLEC→GIRB` 的三元组**（`d9071bf` 修的就是这个）。

### 前缀记录

```
i32 x | i32 y | u32 w | u32 h | u32 payload_len | payload
```

**原点是「有符号」的。** 真实地图里存在 `0xFFFFFFEA`（= −22）、`0xFFFFFFFE`（= −2），
矩形也会超出地图边缘。**客户端不校验，我们也不校验**——曾因按 u32 读并拒绝越界
导致 7 张图打不开（`6540347` 修复）。用 `out_of_bounds_records()` 标注而非报错。

### LLEC（192 字节）—— **不是行走性**

反汇编证明客户端在 `0x4b8d3c` 处 `seek(payload_start + 192)`，**直接跳过，根本没读**。
（`0x609c20` 是 **seek** 不是 read，`0x609c80` 才是 read——这点我错过一次。）
语义未知，别猜。

### MASK

客户端分派器 `0x4b8d5f` 认得 `MASK`，但**8 张样本 + 101 张真实地图里出现 0 次**。
解析器已能容忍。

## 5. GIRB —— 碰撞网格（主战场）

### 几何（已确证，不要再怀疑）

| 项 | 值 |
|---|---|
| 解压后长度 | **2400 字节**（`mx.exe 0x4b8cd8` 处 `new[0x960]`，指针存 `this+0xA4`） |
| 单元 | 1200 个 **u16** |
| 网格 | 40 × 30 |
| 每格像素 | **8 × 8**（320/40 = 240/30 = 8） |
| 空填充值 | `0x8888`（但**不是唯一**填充值，见下） |

交叉验证：1034 有 234 扇区 × 1200 = 280,800 格；扇区补齐后的画布
18×320 × 13×240 = 5760×3120 → 720×390 = 280,800 格。**精确吻合。**

运行期行走性判定在 `0x4bbb00`，索引 **u16** 数组（`cmp %di,(%eax,%ecx,2)`），
唯一调用者 `0x488a49`，判定式 `grid[y*w+x] < threshold`，阈值默认 **1**
（即只有 0 可走）。`0x4baebf` 处确认有 **÷20**。

### 已确证的格值分布（1034，90 个扇区解出）

```
0x8888  99012   ← 空
0x7777   4161
0x6666   2451
0x7888    240
0x7778    232
0x7788    193
...
```

**98.3% 的格是 `0xAABB` 形态**（每个字节都是同一半字节重复，如 `0x88`/`0x77`/`0x66`）。
这说明每字节实际只携带 4 位信息。**这是判断「解出的是真数据还是垃圾」的关键指标**——
改动解压器后必须复查这个分布，否则你可能只是让失败变少而输出全是噪声。

**填充值不唯一**：`0x88`（多数）、`0x77`（2302/2123/2505）、`0x66`（new2_1007）。
任何假设「填充值恒为 0x88」的代码都是错的。

### LZ77 @ `0x60ea90` —— 四个已修 bug

**这四条是本项目的核心资产，每一条都是实测推翻反汇编读数的结果。**

| # | 问题 | 真相 |
|---|---|---|
| 1 | `t >= 0x40` 的长度 | `(t>>5)+1`，**不是** `+2`。因为 `0x60eb85` 在无条件的 2 字节头拷贝前 `dec %eax`。`0x60ec2d` 那几类没有这个预减，所以它们真的是 `accumulated+2`。**不要把两类统一。** |
| 2 | 尾随字面量之后的 `t<0x10` | 走 `0x60ec73` 类（**2 字节**，offset `1+(nb<<2)+(t>>2)`），**不是** `0x60eb29` 类。因为 `0x60ecad` 的 `jmp 0x60eb67` 是**无条件**的。混淆会给每个这类 offset 凭空加 `0x800`。 |
| 3 | **尾随字面量计数** | **不是** `(src[i-2]) & 3`。`offset = 1 + (u16>>2)` 只用掉 16 位操作数的高 14 位，**低 2 位就是尾随字面量个数**，必须由产生它的那个匹配**当场记下**。事后回读 `src[i-2]` 在字面量串之后读到的是**数据字节**。<br>后果：`0x88 & 3 == 0` 恰好正确，所以 5 张样本 + 2504 全解成功；`0x77 & 3 == 3` 立刻全盘崩溃。**这是靠巧合工作的典型。** |
| 4 | **`0x60eb29` 的 offset 基址** | 反汇编读作 `0x801`（=2049），**实测应为 `1`**。实测对比（1034+1035 共 429 扇区）：`0x801` → 129/429，基址 `1` 长度 3 → **144/429**，基址 `1` 长度 2 → 142/429。7 个黄金向量在三个变体下都逐字节一致。<br>**注意：这是经验最优，不是从反汇编推出来的。要坐实还得回 `0x60eb29` 附近重新核对指令。** |

### token 分类表（当前实现）

| token | 语义 |
|---|---|
| `> 0x11` | 字面量串，长度 `token - 0x11` |
| `0x01..0x0f` | 字面量串，总长 `token + 3`（`literal_run_token`，站点 `0x60eabc`） |
| `0x00` | `0xff` 链扩展 + `0x0F + next` |
| `0x10..0x1f` | 匹配；offset `0x4000 + (u16>>2) + ((t&8)<<11)`；**`u16>>2 == 0` 表示流结束** |
| `0x20..0x3f` | 匹配；offset `1 + (u16>>2)`，长度 `(t&0x1f)+2`（带 `0xff` 链） |
| `>= 0x40` | 匹配；offset `1 + ((t>>2)&7) + (byte<<3)`，长度 `(t>>5)+1` |
| `< 0x10`（字面量串后，`0x60eb29`） | 3 字节匹配；offset `1 + (byte<<2) + (t>>2)` ← 实测基址 |
| `< 0x10`（尾随字面量后，`0x60ec73`） | 2 字节匹配；offset `1 + (byte<<2) + (t>>2)` |

**多个 token 读取站点对 `t<0x10` 的语义不同**（`0x60eabc` 字面量串、`0x60eb29` 3 字节匹配、
`0x60ec73` 2 字节匹配）。**建模成单一循环会在约 70% 的非平凡压缩体上产生越界 offset。**

## 7. 下一步该做什么（按优先级）

### P0 —— 继续攻 GIRB token 流

**剩余失败的特征已经变了**，这是关键线索：

```
1034 剩余 127 个 / 1035 剩余 131 个，全部是：
  match offset N out of range at out=N
```

而且**大部分是「差一点点」**，不是彻底失步：

```
样本 s1 len=710  offset=1082  out=1032   ← 只差 50
(offset - out) 分布：82 个落在 [0,500)，19 个 offset 在 [500,1000)
少量极端值（16500 / 34500 / 40000）才是真失步
```

**含义**：某个环节系统性地少输出/多算了几字节，而不是 token 流完全跑偏。

**建议查的方向**（未验证，只是线索）：
1. `literal_run_token()` 的字节数逻辑很可疑。它总是先 `out.extend(buf[i:i+4])`
   再 `total -= 1`，实测对任意 `total` 都输出 `total+3` 字节。这个 `+3` 是对的
   还是巧合？**没验过。**
2. `trail` 目前只在部分匹配类里被写入（`match_hi` 三分支 + 两个短匹配类）。
   检查是否有遗漏的路径让 `trail` 保留上一轮的旧值。
3. `0x10..0x1f` 类的 `((t&8)<<11)` 这个 `0x4000` 偏移在 2400 字节的缓冲里永远越界。
   这一类可能根本不该出现在 GIRB 里，或者我的读法错了。

**方法**：用 `1034` / `1035`（本地就有）反复试，**不需要用户传数据**。
每次改动后必须同时检查：
- 8 张样本无回退（6 张均匀图必须仍 100%）
- 7 个黄金向量仍逐字节一致（`TestGirbGoldenVectors`）
- 解出的格值分布仍是 `0xAABB` 主导（否则是垃圾）

| 「GIRB 体恒定 22 字节」 | 只对 5 张样本 + 2504 成立。1034 有 179 种、1035 有 167 种 |
| 「`t>=0x40` 长度是 `(t>>5)+2`」 | 是 `+1`，`0x60eb85` 预减了 |
| 「只有一种短匹配类」 | 有两种，`0x60ecad` 的跳转是无条件的 |
| 「LLEC 192 字节被读进 `(obj+0x50)+0xC0`」 | `0x609c20` 是 **seek** 不是 read，载荷被跳过 |
| 「`u16()` 是 `IndexError` 的唯一来源」 | `buf[i]` 有 16 处访问、10 处无边界保护，主循环裸读才是通路 |
| 「尾随字面量 = `(src[i-2]) & 3`」 | 是匹配操作数的低 2 位；`0x88` 只是碰巧对 |
| 「`0x60eb29` 基址是 `0x801`」 | 实测是 `1` |
| 「2302 的首字节/结构与样本不同」 | 结构完全相同，只差填充字节 `0x88`→`0x77` |
| 「`read_sector()` 是 `GEPJ→LLEC→GIRB`」 | 必须按 tag 通用走位 |

**共同教训**：**不要把 5 张或 8 张样本上的观察推广成格式规律。** 这犯了两次。

### 环境类

- `objdump --start-address=0x$((16#...))` **输出为空**——bash 的 `$(( ))` 是十进制。
  用 `python3 -c "print(hex(0x... - 16))"`。
- `&&` 链的冒烟测试会静默中断——用 `;` + `echo EXIT=$?`。
- `grep` 在 `script-catalog.csv` 上说 "binary file matches"——用 `csv.DictReader`。
- `pydis26.s()` 偏好 `big5hkscs` → GBK 乱码。
- `.rdata` 里的 "LLEC" 命中 `0x6c89d4`/`0x6c89ea` 是 `DEBUG_COLLECTABLE` 的子串，**假阳性**。
- 一次性扫描曾打印 `LLEC=48`，三次重跑都没复现——**输出污染**。
- **不要把整图渲染进内存**：10000×6000 ≈ 180 MB RGB。必须分块。
  但 `PIL.Image.thumbnail((1280,1280))` 在解码后是安全的：**5600×3000 全图 0.8 秒**。
- 场景名**不在** `script.fls` 里（条目 1301 是 Py2.7 marshal code object）。
  用侧车 JSON。`scriptfls.py` 故意停在 zlib 边界，**不要重新实现 XOR 求解器**。
